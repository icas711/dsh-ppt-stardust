# Разбор расхождений слайдов 2–6 и решение о режиме патча

Дата: 2026-11-19. Проверена рабочая шестислайдовая презентация. Частные тексты, изображения и исходный PPTX остаются в игнорируемой `.test-output/`. Продуктовый импорт/экспорт в этом этапе не исправлялся: добавлены воспроизводимые диагностические проходы и зафиксировано решение о направлении работ.

Последующее решение пользователя: SSIM точной копии рабочего источника — диагностический benchmark, а не общий release gate генератора/редактора. Метрики этого расследования не изменяются; строгие требования поддерживаемых синтетических объектов и сохранности при патче сохраняются. Продуктовые критерии разделены по сценариям в [разделе 6.0 плана](../FEATURE-PLAN-SLIDE-MODEL-2026-11-19.md#60-критерии-выпуска-по-сценариям).

## Контрольные проходы

Сравнение — Microsoft PowerPoint, ширина PNG 1440 пикселей, исходные пропорции. Нет выравнивания изображений, изменения размеров или снижения порога 0,999.

1. **Исходник → SDK load/save без правок:** SSIM **1,000000 на всех шести слайдах**. Из 199 частей ZIP меняется только сериализация `[Content_Types].xml`; набор типов семантически совпадает. Части слайдов, диаграмм, тем, медиа и вложений неизменны по SHA-256 распакованных байтов. Сам ZIP перепаковывается; побайтовое равенство контейнера не заявляется.
2. **Исходник → импорт сцены → новый PPTX:** даёт ровно те же изображения, что **импорт → ZIP шаблона v3 → чтение → заполнение исходными значениями → новый PPTX**. Между двумя результатами SSIM 1,000000 для каждого слайда. Значит, дополнительной визуальной потери в хранении/заполнении шаблона в этом опыте нет. Это не доказывает отсутствие ошибок шаблонов на любых входах.
3. **Патч одного фрагмента текста второго слайда через `setShapeRunText`:** меняется один узел `a:t` в `slide2.xml`, без структурных изменений XML; дополнительно пересериализуется `[Content_Types].xml`. У остальных пяти слайдов SSIM 1,000000. У второго — 0,997096, что ожидаемо при намеренном изменении текста и не является проверкой точности нового текста. Исходный файл не изменён.
4. **Запись неизменённой диаграммы слайда 6 через `setChartSpec`:** PowerPoint не открывает результат. SDK записывает `externalData r:id="rId1"`, хотя в существующих relationships Excel-книга имеет `rId3`, а `rId1` указывает на chartStyle. После диагностического исправления только этой ссылки файл открывается, но SSIM слайда 6 равен **0,958346** даже без изменения данных; остальные слайды — 1,000000. Запись spec полностью перестраивает диаграмму и книгу, теряя оформление. Этот API нельзя напрямую использовать для обещания точного патча чужих диаграмм.

## Дефекты импорта и ограничения модели

| Слайд | Исходный SSIM нового пути | Подтверждённые причины до отрисовки |
|---|---:|---|
| 2 | 0,824410 | 8 нестандартных геометрий и 3 составных объекта «текст + заливка/контур» заменены заглушками. Теряются штриховка сегментов колец и часть параметров цветов/контуров диаграмм. |
| 3 | 0,752402 | Отклонена диаграмма: в исходном XML 3 категории и 10 числовых значений, полного альтернативного кеша категорий нет. Один составной текстовый объект не представлен. Использована палитра другой темы; часть выравнивания подменена значением по умолчанию. |
| 4 | 0,872352 | Один составной текстовый объект и 2 OLE graphicFrame не представлены. Унаследованные цвета неверны; у нескольких фигур с текстом импорт выставляет центр вместо левого края. |
| 5 | 0,861232 | Один нумерованный текстовый блок, один составной текстовый объект и 4 OLE graphicFrame не представлены. Унаследованные цвета взяты из другой темы. |
| 6 | 0,939685 | Все объекты распознаны, но у 10 серий диаграммы отсутствуют исходные тематические цвета с shade/tint. У текстового объекта 97 потерян `cap="all"`: исходник показывает прописные, сцена содержит исходную строку без свойства регистра. |

Точки в коде:

- `deck-pptx-scenes.mjs`: палитра получается через `getPresentationTheme(pres)`. В источнике слайды 3–5 используют `slideMaster3.xml → theme3.xml`, где `dark1=#3E3E41`; первая тема имеет `dark1=#000000`. Одной глобальной темы и карты цветов слайда недостаточно. Нужен resolver цепочки slide/layout/master/theme и themeOverride, затем разрешение наследуемых свойств каждого фрагмента текста.
- `deck-legacy-scene.mjs`, `textElement`: `properties.align ?? (textbox ? 'left' : 'center')` вносит центр для обычной фигуры без явного `algn`. В сцене уже записано неправильное выравнивание; сериализатор воспроизводит его. На слайде 4 это подтверждено объектами 2 и 33 и нативными свойствами PowerPoint.
- `deck-native-objects.mjs`, `readNativeChart`: SDK spec не передаёт часть исходных schemeClr/трансформаций и patterned fills. В частности, все 10 series.color слайда 6 отсутствуют уже на границе импорта. Нужны явные диагностики потерь, разрешение цветов и расширение контракта для заливки/контура/оформления точек.
- `deck-legacy-scene.mjs`, `textStyle`, и общий контракт: `cap` не переносится. Это ограничение сразу импорта, модели и экспорта; одной правкой промпта его не устранить.
- Для составного объекта следует передавать фигуру и текст согласованной группой с исходным порядком, а не отклонять весь объект. Для нестандартной геометрии требуется отдельный контракт путей/превью. Для нумерации — сохранение вида и начального номера.
- Несогласованный кеш диаграммы не следует чинить выдуманными категориями. Проверять разрешённую связанную XLSX-книгу и её диапазон; при невозможности восстановления оставлять диагностируемое ограничение. Патч режима не требует пересоздавать такую диаграмму, пока её данные не меняются.

## Дефекты отрисовки и измеренный вклад

`deck-scene-pptx.mjs` превращает unsupported без растрового превью в текстовую фигуру с полным сообщением об ошибке. На узких вертикальных рамках текст переносится по буквам, а на коротких плашках выходит за пределы и перекрывает соседей. Это самостоятельная проблема fallback-отрисовки поверх потерь импорта. Подробную причину следует показывать в отчёте/инспекторе, а на слайде использовать ограниченный по рамке индикатор или проверенное превью.

Выполнены **два независимых** диагностических изменения сцены; продуктовый код не менялся:

| Слайд | Базовый SSIM | Скрыты только unsupported-заглушки | Восстановлены только доступные solid-цвета диаграмм |
|---|---:|---:|---:|
| 2 | 0,824410 | 0,880255 | 0,825959 |
| 3 | 0,752402 | 0,763332 | 0,752402 |
| 4 | 0,872352 | 0,882602 | 0,872352 |
| 5 | 0,861232 | 0,881714 | 0,861232 |
| 6 | 0,939685 | 0,939685 | 0,975316 |

Скрытие заглушек не возвращает исходное содержимое и не является исправлением импорта. Цвета восстановлены диагностическими фигурами-пробами: исходный solidFill разрешён SDK в контексте исходного файла и явно передан в сцену, затем выполнен обычный новый экспорт. Нет растровой подмены диаграмм, изменения значений или пересадки XML исходной диаграммы в результат. Patterned fills не подменялись придуманным цветом. Улучшения SSIM не складываются и не являются процентной оценкой вклада причин.

На слайде 6 область диаграммы — крупнейшая область ошибки: 141 412 пикселей с расхождением канала >16 в исходном новом экспорте; региональный SSIM 0,679767. Области могут пересекаться, поэтому их ошибки нельзя суммировать. Остаток после восстановления цветов ещё требует отдельных контрольных проходов по размещению plot area, границам серий и тексту. Приписывать весь остаток геометрии пока нельзя.

Из 42 прежних сравнений нативных агрегированных свойств нельзя выводить «42 визуальных дефекта»: значения Mixed для целой текстовой фигуры зависят в том числе от пустых/конечных фрагментов. Есть отличия этих свойств даже на пиксельно идентичном первом слайде. Следующий усиленный golden должен сравнивать непустые фрагменты по исходным ID/диапазонам и измерять переполнение текста, сохраняя отдельный пиксельный gate.

## Решение: добавить отдельный режим патча, начиная с текста

Рекомендация — **да**. Для правки чужого файла с сохранением оформления это отдельный путь работы. Создание переиспользуемого шаблона и редизайн остаются на объектной модели; они требуют извлечения смысла и перестроения структуры. Режим должен выбираться явно, без скрытого переключения при неудаче импорта.

Первая версия патча:

1. Сохранить ссылку на пользовательский источник, SHA-256 и версию карты адресов. Исходник считать неизменяемым, не копировать в библиотеку/общие ассеты и не помещать в ZIP переиспользуемого шаблона.
2. Адресовать `slidePart + shapeId + paragraph/run` и проверять ожидаемый старый текст/хеш. Несовпадение, дубликат или неподдерживаемая операция — ошибка без записи. Не искать объект по совпадению видимого текста.
3. Поддержать замену текста в существующем фрагменте с сохранением его `rPr`, `pPr`, размера страницы, групп, тем и relationships. Замена нескольких фрагментов/новых абзацев требует отдельного явного контракта распределения форматирования.
4. Сохранять новый файл атомарно, исходник не перезаписывать; хранить патчи и undo. Отчёт перечисляет все изменённые части. Лимиты, внешние relationships и вложения проверять до правок; ничего не исполнять и не загружать извне.
5. На выходе проверять allowlist изменений пакета, доступность файла в PowerPoint и SSIM нетронутых слайдов = 1. Для изменённого слайда проверять сохранность вне согласованных областей и переполнение; весь слайд после намеренной смены текста не обязан совпадать с исходником по SSIM.
6. Данные диаграмм добавлять следующей версией: точечное изменение соответствующего cache и разрешённой XLSX с сохранением исходного chart XML/relationships. Нынешний `setChartSpec` для этого пути не подходит. Синтетическая фикстура должна иметь XLSX relationship с ID, отличным от `rId1`, chartStyle, theme colors и неподдерживаемые в сцене детали оформления.

### OLE — согласованное продуктовое решение

Диагностический load/save и текстовый патч сохранили **4 исходных OLE .bin побайтово**. Они не выполнялись, не интерпретировались и не превращались в ассеты. Это свойство контрольной копии исходного ZIP, **не разрешение переносить OLE в продуктовый шаблон/генерируемый PPTX**.

После обсуждения пользователь согласовал исключение: в режиме патча **сохранять исходные разрешённые OLE непрозрачно и побайтово внутри пользовательского PPTX**, показывая их наличие и неизменность в отчёте. Не исполнять, не интерпретировать, не извлекать в отдельные файлы и не допускать в ZIP шаблона/новую генерацию. Прежнее предложение отклонять файл только из-за наличия OLE отменено.

Обычные гиперссылки разрешены; VBA и остальные внешние relationships, неизвестные части/content types/связи вне явного списка отклоняются. [Контракт патча](../PPTX-PATCH-CONTRACT.md) содержит точные списки внешнего пакета и вложенных XLSX и критерии приёмки. Рабочий пример имеет четыре OLE-бинарника, без VBA и внешних relationships; его допуск должен подтвердить будущий валидатор всей политики. Реализация ещё не согласована и не начата; сейчас изменены план и контракт. Генератор и редактор шаблонов остаются основным продуктом.

## Очерёдность работ

1. Исправить разрешение темы/наследования и fallback выравнивания; добавить синтетические фикстуры нескольких мастеров и обычных фигур с текстом.
2. Убрать выход диагностических заглушек за рамки; отдельно реализовать compound text+shape и нумерацию. Добавить `cap` в единый контракт.
3. Сохранять цвета, transforms, контуры и заливки диаграмм; ввести явный loss-report для неподдерживаемого оформления. Повторить golden слайдов 2–6 после каждого изменения, не менять порог.
4. После отдельного согласования реализации добавить текстовый патч по принятому контракту с неизменным сохранением разрешённых OLE. Затем — точечные патчи chart cache/XLSX с отдельной приёмкой. Пакет 6C генератора и редактора шаблонов не ждёт этой работы.

## Воспроизведение

```powershell
node scripts/diagnose-pptx-fidelity.mjs SOURCE.pptx OUTPUT_DIRECTORY --render --ablations
python scripts/diagnose-pptx-fidelity.py OUTPUT_DIRECTORY TEMPLATE_GOLDEN_DIRECTORY
```

Первый скрипт исследует текстовую правку на слайде 2 и повторную запись диаграммы на слайде 6; для другого источника эти контрольные объекты могут отсутствовать. `--render-only=NAME` позволяет отдельно повторить контроль в каталоге того же источника. Полный запуск возвращает ненулевой код при ошибке нативного рендера, сохраняя причину в `controls.json` и продолжая остальные контроли. В данном файле ошибка `chart-rewrite` ожидаема и является результатом расследования. Python измеряет только полностью отрендеренные варианты; отсутствие рендера не считается SSIM=1.

Требуются Windows/PowerPoint и зависимости Python существующего golden. Локальные подробности: `.test-output/fidelity-diagnosis/diagnosis.json`, `controls.json`, `imported-scenes.json`, PNG/PPTX контрольных вариантов. Каталог содержит исходные вложения и частный контент; не публиковать. Обезличенные числа сохранены рядом в `pptx-fidelity-diagnosis-2026-11-19.json`.

Полный набор предыдущего этапа: 411/411 тестов. В этом этапе проверены синтаксис диагностических скриптов и реальные нативные контрольные проходы; продуктовый код после полного набора не менялся.
