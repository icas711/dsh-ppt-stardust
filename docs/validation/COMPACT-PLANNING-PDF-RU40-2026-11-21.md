## Планирование B/C

Причина асимметрии опыта 04 — проверка maxPlannedSlides/purpose только на стадии scenario. В runner 4 одинаковые ограничения применяются и на spec B/C; тип visual проверяется на соответствие заданному visualType. У обоих режимов одинаковая инструкция: планировать смысловые группы, полный реестр передавать одной таблицей, страницы делит движок. Параметр остаётся явным opt-in вызывающей стороны; произвольные задачи без него и обычный tableSpec/visualSpec не получают нового лимита.

При spec-feasibility выдаётся диагностика уровня spec.slides без отдельных slideId: модель возвращает полный объект, что позволяет слить старые плановые слайды. Экспорт до успешной проверки не выполняется. Исправление входит в прежний общий бюджет двух попыток. Повторное нарушение три раза завершает задание budget-exhausted без экспорта.

Регрессия моделирует четыре таблицы 8+8+8+6, как в опыте 04: первый spec отклонён, полный исправленный spec с одной таблицей принят; все 30 строк точно сохраняются после физической пагинации. Дополнительно проверены неверный purpose и неверный тип visual в B/C, полное исправление и исчерпание бюджета. Компоненты остаются 16, runner повышен до 4, плагин — ru.40.

## Диагностическая привязка будущего автоматического PDF

После успешного автоматического PDF результат операции содержит `pdfRender`: sourceSha256, pdfSha256, backend/rendererVersion при наличии, missingFonts, visual:not-verified. Хеш PDF вычисляется по тем же байтам, которые копируются в выдачу; sourceSha256 ранее сопоставляется с текущим PPTX под блокировкой. Структура не содержит путей кеша и не меняет состав выдаваемых файлов. При ошибке PDF метаданные успеха отсутствуют. Это сведения текущей успешной операции, а не восстановленная история старых проектов. Experiment report сохраняет их вместе с artifacts.

Регрессия проверяет совпадение хешей исходного/выданного файла, версию/backend, отсутствие путей кеша и отсутствие pdfRender при ошибке. Полный npm test со сборкой: 629 тестов, 627 passed, 2 skipped, 0 failed. Старые серверные report без pdfRender не получают вымышленных значений.

## Дальнейшая проверка на сервере

После обновления ru.40 при необходимости диагностики достаточно повторно отрендерить сохранённый исходный PPTX через ppt_render с format:pdf; новую презентацию генерировать не нужно. Сохранить PDF и точный ответ инструмента с sourceSha256/backend/rendererVersion/receiptPath. Сравнить sourceSha256 с исходным хешем выше. Если дефект повторится, прочитать относящуюся к этому рендеру квитанцию; архив старого результата не позволяет восстановить её задним числом. Повтор всей сравнительной серии не назначается.
