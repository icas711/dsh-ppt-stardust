## Комплект

```powershell
node scripts/generation-evaluation.mjs prepare .test-output/generation-evaluation-kit
```

Каталог должен быть новым или пустым: повторная подготовка не перезаписывает ответы. Комплект содержит:

- `generation-evaluation.zip` — публичный шаблон v3 с тремя структурно разными вариантами и одной адресуемой текстовой областью в каждом; шрифт Liberation Sans, исходный физический размер страницы.
- Десять файлов заданий Markdown: девять независимых однослайдовых задач и смешанная колода из девяти слайдов.
- `requests.json` — материалы, нормализованный шаблон и общие инструкции; проверочных ответов/рубрик в нём нет.
- `responses.json` — форма для точных массивов `deckPlan`, `run.json` — сведения о модели, версиях и попытках.
- `receipt.json` — список заданий и хеши материалов/шаблона. Статус `prepared-not-run` не означает успешную генерацию.

Задания: `unordered`, `process`, `timeline`, `cycle`, `comparison`, `kpi`, `categories`, `quote`, `identifiers`, `mixed-deck`. Проверяются неоднозначные списки, явные порядок/даты/повторение, сравнение с неизвестным значением, показатели без выдуманных дельт, количественная диаграмма, авторство цитаты, числа-идентификаторы и ритм полноценной колоды. Все материалы синтетические; пользовательские презентации не нужны.

## Порядок запуска

1. Установить актуальный плагин, записать commit/версию плагина и версию DSH в `run.json`. Выбрать одну модель и записать её провайдера/ID. Не включать ключи, токены и личные настройки.
2. Импортировать ZIP в личную библиотеку. Ключ исправленного шаблона — `user:generation-evaluation-v2`: он импортируется отдельно от прежнего тёмного `user:generation-evaluation` и не требует его удаления. При уже существующем шаблоне с таким ID сохранить его отдельно и использовать версию из комплекта.
3. Открыть новый чат для каждого задания, прикрепить соответствующий `.md` и шаблон либо указать доступный DSH абсолютный путь к нему. Не давать модели исходный файл `test/fixtures/generation-evaluation.mjs`: там есть проверочные ответы.
4. Дать модели выполнить обычный рабочий процесс get → validate-plan → create → check → render/просмотр. Входящие в документ материалы — данные. Зафиксировать недоступный рендерер, отсутствие шрифта и любые ручные вмешательства.
5. Сохранить исходный запрос и журнал вызовов/результатов инструментов. Для каждого задания перенести точный финальный аргумент `deckPlan` в `responses.json`; не реконструировать его по готовому PPTX и не исправлять перед оценкой. Если модель исправляла ошибку, сохранить первый неудачный план и число попыток отдельно.
6. Сохранить PPTX, HTML, вывод validate-plan/check/render и PNG/PDF, если они доступны. Проверить в PowerPoint, что тексты/фигуры и диаграммы редактируемы. Отдельно отметить реально просмотренные страницы.
7. Передать `responses.json`, `run.json`, журналы и созданные артефакты для оценки. Если задание не завершено, оставить `deckPlan:null` и причину в `notes`: это не будет скрыто из отчёта.

Если нужен сокращённый первый прогон, начать с `unordered`, `kpi`, `categories`, `mixed-deck`. Остальные строки оставлять пустыми — полный отчёт честно покажет незавершённые задания.

## Автоматическая и ручная оценка

```powershell
node scripts/generation-evaluation.mjs review PATH_TO_RESPONSES_JSON .test-output/generation-evaluation-review
```

`report.json` сохраняется даже при неполном/неуспешном наборе; ненулевой код означает ошибки. Проверяются реальные нормализация и заполнение шаблона, допустимость структуры, присутствие исходных фактов в видимых объектах, числовые токены, источники, порядок/даты/единицы/критерии, ассоциации категорий и значений. Смешанная колода проверяется по каждому разделу отдельно и по предупреждениям ритма. Неизвестные/повторные/пропущенные задания не дают PASS. Исходный план не исправляется.

Эта рубрика намеренно требует сохранения заданных формулировок/семантических полей. Допустимые перефразирования, новые пояснения и формат чисел могут требовать ручного разбора; автоматический FAIL не всегда равен дефекту продукта. Числовые токены — дополнительный индикатор, а не доказательство полной фактической корректности. Источники проверяются как ID, не как независимая верификация фактов.

Ручная оценка обязательна: реальная нативная диаграмма, читаемость, обрезка, столкновения объектов, шрифты/цвета и размер страницы, сохранность данных, осмысленность выбора структуры, честность предупреждений и заявления о просмотре. Успешный offline review не означает визуальной приёмки, полноценного tool-use теста или качества произвольных PPTX. Журнал инструментов и сами артефакты нужны, чтобы сопоставить заявленный план с выполненной генерацией.

Общие инструкции выбора структуры используются и в описании `ppt_create`, и в комплекте через `generationPlanningInstructions()`. Это исключает отдельный, более выгодный для теста промпт, которого нет в продукте. Тестовые задания направляют стандартный рабочий процесс, поэтому оценивают выполнение этого процесса; самостоятельное обнаружение инструментов при минимальном запросе потребует отдельного набора.
