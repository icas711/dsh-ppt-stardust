Дата: 20.11.2026. Обновлено: 21.11.2026. Обычные tableSpec и visualSpec реализованы и проверены в перечисленных серверных сценариях: восемь типов, смешанные колоды, A4, изображения, диаграммы с одним/двумя рядами, правка и отмена. Актуальная версия ru.39, компоненты 16; серверная тройка chart/dark подтверждена (§41). Серверный PDF со встроенным TT Moscow Economy подтверждён архивом 1825; шрифтовая проверка закрыта (§38). A/B/C остаётся отдельным сравнительным прототипом без объявленного общего победителя. Итог обычного пути — §35, последующие исправления — §§36–38, сравнительный пилот — §§39–41.

## Согласованные требования

- Целевая модель — `glm-5.3-flash`. Живые задания пользователь запускает в DSH и передаёт результаты.
- Модель генерирует компактный JSON. Существующий движок рассчитывает композицию и выпускает HTML/PPTX/PDF, если PDF-рендерер доступен. Генерация Python-кода не требуется.
- Главный критерий — скорость до принятого результата при приемлемом качестве; стоимость измеряется отдельно.
- Сразу поддерживаем пользовательские PPTX-шаблоны через существующий импорт, сохраняя размер страницы, оформление и типографику в пределах подтверждённых возможностей импортера.
- Роль каждого вложения модель обязательно уточняет у пользователя: содержание, оформление или обе роли. Приложенный `Proekty_II.pptx` автоматически шаблоном не назначен.
- Существенные факты сохраняются; число слайдов можно увеличивать. Единого лимита 30 слов нет.
- Первая версия: process, cards, chart, timeline, comparison, big_number, table, image; иконки из каталога по ID.
- Числа и факты — из материалов. Синтетика разрешена только в явно обозначенных демонстрациях.
- После первого ответа допускаются максимум два дополнительных обращения для исправления. Координаты исправляет движок.

## 1. Сравниваемые режимы

| Режим | Ответ модели | Сборка |
| --- | --- | --- |
| A | Текущая свободная композиция: содержание, геометрия и стили scene | Действующий экспорт |
| B | Один запрос → семантический JSON | Детерминированные компоненты → scene → действующий экспорт |
| C | Сценарий → отдельный запрос семантического JSON | Те же компоненты и экспорт, что у B |

Материалы, модель, шаблон, требования и лимиты исправлений одинаковы. Двухэтапность — проверяемая гипотеза, не обещание ускорения. Текущий режим сохраняется без изменения поведения.

## 2. Уточнение задачи

До генерации DSH ask_user_question уточняет цель, аудиторию, язык, подробность, роль вложений, шаблон, количество слайдов/право его увеличить, обязательные факты и недостающие сведения. Уже полученные ответы не спрашиваются повторно без причины.

Результат — общий структурированный brief для A/B/C. Время общения с пользователем учитывается отдельно. Самодекларация модели «вопросы заданы» не доказывает вызов инструмента: строгий технический барьер требует подтверждённой истории DSH, которой текущий интерфейс плагина может не предоставлять.

## 3. Подготовка шаблона

Повторно использовать импорт v3, извлечение ассетов и разрешение designLayout/purpose. Подготовить компактный профиль: физический размер, фоны, фиксированные объекты, шрифты/палитра, референсы обложки/содержимого/завершения, текстовые ориентиры, области оформления.

Размер шаблона сохраняется; принудительного 16:9 нет. До генерации проверять пригодность и сообщать неподдержанные объекты/потери. Произвольный входной PPTX не означает гарантированное точное воспроизведение всех возможностей PowerPoint. Отсутствие cover-референса не обходить сменой семантического purpose; пользователь может явно выбрать существующий designLayout.

Кеш профиля зависит от содержимого шаблона, версии импортера и версии профиля. Холодный и повторный запуск измеряются раздельно. Для разных пользователей сохраняется существующая изоляция доступа.

## 4. Контракт generation-spec-v1

Версионированный JSON: title, lang, режим factual/demo, slides. Слайд содержит стабильный id, purpose, title, visual, опциональные notes/designLayout. visual — дискриминируемое объединение восьми типов. Координаты, шрифты, цвета, XML и исполняемый код запрещены схемой.

sourceRefs привязываются к внешнему реестру исходных фрагментов. assetId и iconId — к реестрам ассетов/иконок. Реестры предоставляет вызывающая сторона, а не ответ модели. Наличие ссылки не доказывает истинность утверждения: полнота и точность относительно материала проверяются отдельно.

Для process требуется явный порядок; timeline — реальные упорядоченные даты; comparison — общие критерии и явный null для отсутствующих значений; chart — категории, единицы и числовые серии; big_number — число, единица и пояснение. Синтетические источники принимаются только при mode:demo, с видимым раскрытием при последующей сборке.

Повторно использовать deck-semantic.mjs и deck-structured.mjs. Таблицы и изображения сохраняются как содержательные данные до этапа размещения; геометрия в этот контракт не входит.

## 5. Компоненты и размещение

Собрать process, cards, chart, timeline, comparison, big_number, table, image. Для основных компонентов предусмотреть несколько композиций под размер страницы и объём текста. Иконки — по ID из локального каталога, изображения — существующие ассеты без base64 в ответах модели. Новое получение изображений — отдельная явная возможность с отдельным измерением времени.

Путь: spec → проверка → референс шаблона → область содержимого → композиция → геометрия → стили → scene → существующий экспорт.

При переполнении пробовать другую композицию или разрешённое разбиение. Не удалять факты и не уменьшать шрифт неограниченно. Неразрешимая вместимость — адресная ошибка. Не считать sample-область шаблона обязательной фиксированной ёмкостью; учитывать реальную графику и соседние блоки.

Сохранить нативную редактируемость схем, таблиц, текста и диаграмм. Декоративность сама по себе не критерий качества.

## 6. Проверки и исправления

Разделить: JSON/контракт; исходные факты/числа/единицы/порядок/источники; геометрию/вместимость; экспорт/редактируемость. Ошибка содержит code, path, slideId и пояснение.

Лимит — первый ответ плюс максимум два исправления для всего задания, включая двухэтапный режим. Отправлять модели только затронутую часть и необходимые источники. Не исправлять импорт шаблона переписыванием содержания. Сохранять все ответы, ошибки и ручные вмешательства. После исчерпания лимита выдавать честный статус; правильный JSON не равен принятой презентации.

## 7. Комплект ручного запуска в DSH

Подготовить задания, материалы, точные промпты A/B/C, версии контракта/компонентов/плагина, форму run-журнала, сохранение первых ответов и исправлений, артефакты и оценщик. Адаптировать scripts/generation-evaluation.mjs: старый deckPlan не является проверкой нового пути.

Задания: предоставленный материал и независимые контролируемые случаи для восьми типов; длинный русский текст, неполные сведения, некорректная диаграмма, перегрузка. Шаблоны: светлый, тёмный, с выраженным декором, нестандартного размера. Частные материалы не добавлять в публичные fixtures без отдельного основания.

## 8. Измерения

Главное — время до результата, прошедшего приёмку, включая исправления. Отдельно фиксировать время первого ответа, полное время, число обращений, входные/выходные токены, стоимость при наличии данных провайдера, успех с первой попытки, сохранность фактов, визуальные дефекты.

Сначала небольшой пилот A/B/C, затем минимум три повторения перспективных вариантов. Чередовать порядок запусков, изолировать память/рабочие папки, записывать точные версии. Холодный импорт и кеш разделять. Не выдавать оценку токенов по длине текста за фактический биллинг. Незавершённые запуски сохранять в отчёте, не исключать из статистики.

## 9. Приёмка

Обязательные факты сохранены; нет добавленных неподтверждённых чисел/источников; файлы открываются; нет критической обрезки/перекрытий; текст читается; подтверждённый стиль шаблона сохранён; данные и схемы редактируемы. Для прототипа требуется визуальный просмотр экспортированных слайдов. XML/структурные тесты его не заменяют.

Среди прошедших порог выбирать самый быстрый режим. При преимуществе в пределах разброса признать отсутствие убедительного победителя. Числовые целевые пороги ускорения определить после пилота, до подтверждающего прогона.

## 12. Профиль шаблона — выполнено

Добавлен `deck-generation-profile.mjs`: подготовка профиля из разрешённого шаблона v3 или через существующий импорт PPTX; фактический размер, фоны, палитра/типографика, референсы, compositionGuides и рамки фиксированного декора. Проверяются байты ассетов, видимые потери оформления, превью и отчёт импортера. Неизвестная доступность шрифтов, отсутствие отчёта и неподтверждённая визуальная приёмка отмечаются явно.

Кеш в памяти ограничен по числу записей/объёму, разделён scope и зависит от исходных байтов, manifest/ассетов/отчёта и версий. Прямой повтор того же PPTX пропускает импорт; чтение/хеширование, импорт и построение профиля измеряются отдельно. Это структурная проверка кеша, не замер ускорения генерации на модели. Авторизация остаётся у вызывающего сервиса; автоматического подключения к DSH нет.

CLI `scripts/generation-profile.mjs` поддерживает явный просмотр PPTX и ZIP. [Описание API и ограничений](GENERATION-TEMPLATE-PROFILE.md). Исходный пользовательский `Proekty_II.pptx` как шаблон не использовался; роль вложения по-прежнему должна быть уточнена при генерации.

Проверки: 13 новых тестов профиля; полный `npm test` со сборкой — 528 тестов, 526 passed, 2 skipped, 0 failed. Проверены светлая/тёмная и нестандартная страницы, ассеты/превью, отражённый текст и вложенные группы, реальный импорт синтетического PPTX, кеш/изоляция/отмена. Визуальная приёмка и живые вызовы модели не выполнялись. Следующий пакет — восемь компонентов и преобразование содержимого в scene.

## 14. Режимы B/C, исправления и журнал — выполнено

Добавлен изолированный `deck-generation-run.mjs`: B получает spec одним плановым вызовом, C сначала проверяет сценарий, затем получает spec. Два исправления общие для задания; переход между стадиями C бюджет не сбрасывает. Максимум вызовов — 3 для B и 4 для C с учётом двух плановых стадий. Адресное исправление заменяет строго выбранные слайды, сохраняя остальные; исходный контекст сужается до связанных фрагментов, когда ссылки позволяют это определить. Геометрию/импорт модельным переписыванием содержания не исправляем.

Последовательный журнал сохраняет запросы, точные ответы и metadata/usage, диагностику, время вызовов, сведения о ручных вмешательствах, отчёт композиции, артефакты и честный статус остановки. Ошибка сохранения журнала останавливает работу. Внешний проверяющий фактов подключается отдельно; техническая сборка всегда имеет `acceptance:not-verified`.

CLI `scripts/generation-run.mjs` воспроизводит сохранённые ответы и экспортирует через действующий движок, сохраняет входы/JSONL/result и не перезаписывает существующий запуск. [Контракты, бюджет, журнал и команды](GENERATION-RUN.md). Production `ppt_create` не подключён к новому пути, живых запросов и установки в DSH нет.

## 15. Воспроизводимый ручной комплект A/B/C — выполнено

В `scripts/generation-evaluation.mjs` добавлены отдельные команды `prepare-compact`, `record-compact`, `advance-compact`, `review-compact`. Старый `deckPlan`-оценщик сохранён для прежнего набора; новый путь воспроизводит A через свободные scene-объекты и существующий экспорт, B/C — через spec, runner и компоненты. Локальные команды не вызывают модель. После каждого точного ответа из DSH команда выдаёт следующий scenario/spec/repair-промпт либо экспорт/честный статус остановки; максимум два исправления общие для задания. Исходные ответы, снимки, журнал и результаты сохраняются с проверкой хешей; скрытого начала задания заново нет.

Подготовлены 12 независимых синтетических заданий: восемь типов, длинный русский текст, неизвестные сведения, ошибочная рекомендация pie и реестр из 30 строк. ### Актуальная инструкция

Для табличной колоды использовать tableSpec, для сочетания поддерживаемых типов visualSpec. Нужен согласованный доступный schema 3 шаблон. Факты, числа, единицы, оговорки и исходные изображения сохраняются; неизвестное не превращается в ноль. Подготовленный проверенный запрос предпочтительно передавать через requestFile/requestSha256 без повторного набора моделью. При генерации из нового текста проверка sourceRefs подтверждает привязку, а не фактическую полноту извлечения.

В pie исходная сумма и единица обязательны, проценты добавляются только при showPercent:true. Число и единица держатся вместе, новые подписи не используют длинное тире. Для числовой правки использовать elementUpdates с chartValues:number[][] и актуальными deckPath/expectedRevision, а не переписывать большой chart. Undo получает ревизию успешной правки. ### Границы результата и оставшаяся работа

- Приёмка относится к перечисленным входам и шаблонам. Любой PPTX, иной размер, длинная подпись или графика шаблона не получают автоматической гарантии качества.
- SourceRefs и контрольные суммы не доказывают истинность или полноту исходных фактов. Модель может ошибиться при извлечении нового материала; синтетические данные требуют demo с видимым раскрытием.
- Поддержанные изображения содержатся целиком, экспортируемые диаграммы/таблицы нативные. Старые и ручные pie без amountLabels не мигрируются автоматически; собственный текст подписей обновляется через плагин, а не при внешней правке PPTX в Office.
