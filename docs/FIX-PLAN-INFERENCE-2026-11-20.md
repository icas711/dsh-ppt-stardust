# План исправлений: ошибки инструментов при генерации и правках

Дата: 20.11.2026. Статус: исправления реализованы и проверены локально; живая интеграция с DSH, визуальная приёмка и замеры инференса остаются открытыми.

Основание: три пользовательских лога `ppt_create` / `ppt_edit` и локальное воспроизведение на текущем коде. Версия установленного на сервере пакета и полный сохранённый JSON пользовательского проекта не предоставлены. Третий лог содержит вывод проверки нового проекта: ревизия 0, восемь слайдов, фигуры и изображения присутствуют, HTML/PDF/PPTX записаны несмотря на ошибку ответа. Удаление фигур предыдущими правками описано в тексте модели; сырой результат этой проверки в приложенном фрагменте отсутствует, но механизм подтверждён кодом и локальным воспроизведением.

## P0. Ответы инструментов должны быть JSON без потерь

Причина: в `skills/dsh-ppt/scripts/deck-advanced.mjs` функции `result()` и `checkDeck()` формируют метаданные слайда через `title: s.label ?? s.title`. У scene-слайда `label` необязателен, а поле `title` отсутствует. Ответ получает собственное поле `title: undefined`; JSON-сериализация удаляет его. Исполнитель возвращает объект без очистки. В новом логе все восемь входных слайдов без `label`; свободная композиция шаблона не назначает его автоматически.

- [x] Выбрать и одинаково применить контракт отсутствующего заголовка: строка по умолчанию либо отсутствие поля. Не требовать от модели искусственного `label` для обхода дефекта ответа.
- [x] Проверить реальные результаты `ppt_create`, `ppt_edit`, `ppt_check`, `ppt_undo` и ветку редактирования без изменений на JSON round-trip; устранить другие `undefined` и невалидные JSON-значения, если они обнаружатся.

Приёмка: ответы всех перечисленных операций проходят проверку без потерь; создание и последующая правка scene-проекта без `label` не дают `returned invalid output: value is not lossless JSON`.

## P0. Учитывать сохранение операции до ошибки доставки ответа

Проверка ответа хостом находится за этой границей и не откатывает сохранённую операцию. Локально правка вернула `title: undefined`, но ревизия уже выросла с 0 до 1.

## P0. Уточнить контракт редактирования и предотвратить потерю объектов

Первый лог: модель сначала передала `elements` рядом с `slide`, пропустив обязательный `patch`; затем передала элементы без `frame`. Обёртка `patch` и обязательный `frame` уже описаны в схеме. Ошибки аргументов доходят до проверок движка; по логу нельзя установить, почему хост не отклонил их раньше.

Критическая семантика: `patch.elements` полностью заменяет массив, а не объединяет объекты по `id`. При передаче трёх изменённых элементов остальные будут удалены. Локально замена массива из двух объектов одним оставила один объект в сохранённом проекте.

В третьем логе модель сообщает о потере всех фигур и декора на затронутых слайдах: остались текстовые объекты. В отличие от создания по `templateId`, редактирование не вызывает `composeSceneTemplateSlides()` и не добавляет декор заново по `designLayout`. Наличие ссылки на макет не восстанавливает удалённые элементы. Приоритет повышен из-за потери содержимого.

Не менять молча существующую семантику массивов; в рамках реализации выбран совместимый отдельный режим `patch.elementUpdates:[{id,changes}]`: изменяет существующие объекты, сохраняет остальные и не допускает смены ID/типа. Прежняя полная замена `elements` не изменена; совместимость проверена тестами.

Решение по контракту в рамках запроса на реализацию: добавлен отдельный `elementUpdates`, полная замена массивов остаётся прежней. Переданные поля заменяются целиком, кроме объединяемого `textStyle`; изменение отдельных runs требует сохранения остальных абзацев и runs.

## P0. Явный цвет текста должен перекрывать унаследованный colorSpec

Третий лог использует обход: модель добавляет `colorSpec:{base:цвет,transforms:[]}` ко всем runs при повторном создании. Обнаружена и локально воспроизведена причина необходимости такого обхода. `composeSceneTemplateSlides()` наследует стили текста из образца, включая `colorSpec`. `mergeSceneTextStyles()` объединяет поля через `Object.assign`, поэтому новый `color` не удаляет старый `colorSpec`. В `deck-scene-pptx.mjs` функция `runProperties()` предпочитает `colorSpec` полю `color`. В HTML `fontCss()` использует `color`, поэтому возможны разные цвета в HTML и PPTX.

Минимальное воспроизведение: базовый стиль `{color:'#000000',colorSpec:{base:'#000000',transforms:[]}}` и run `{color:'#FFFFFF'}`. После слияния `color` белый, `colorSpec` чёрный; фактический XML содержит `<a:srgbClr val="000000">`.

- [x] Определить единый приоритет цвета при наследовании: явно заданный в более конкретном стиле `color` без нового `colorSpec` должен сбрасывать унаследованный `colorSpec`. Проверить уровни шаблона, элемента и run, включая слияние в композиции, а не только экспорт.
- [x] Сохранить импортированные цветовые transforms, когда явного переопределения нет. Зафиксировать правило для явно переданных вместе `color` и `colorSpec`.
- [x] Согласовать вычисление эффективного цвета в HTML и PPTX; проверить белый текст на цветной плашке и красные метки, а также наследование transforms без переопределения.
- [x] Проверить XML итогового PPTX на фактический цвет и HTML на эффективный CSS-цвет; не требовать дублирования цвета через `colorSpec` от модели как штатного решения.
- [ ] Визуально сравнить рендер текущего PPTX с HTML. В локальном окружении нет официального LibreOffice Kit, PowerPoint и установленного LibreOffice; проверка XML/CSS не заменяет визуальную приёмку.

Приёмка: явный белый/красный цвет run сохраняется после применения шаблона и в обоих форматах; исходные цветовые эффекты сохраняются там, где переопределения нет.

## P1. Восстановление не должно незаметно подменять идентичность проекта

В третьем логе модель выбирает `ppt_create overwrite:true`, считая это заменой повреждённой тройки. Вывод команды показывает другой внутренний проект: прежний `e9a13d7d-247f-4ac4-a6f4-70962c210ff4`, новый `df68585a-9721-4abf-9fae-8000d999ee52`, ревизия 0. Код подтверждает: каждое создание назначает новый `deckId`, пустую историю и новый внутренний каталог; `overwrite` управляет коллизией имени выдаваемых файлов, а не редактированием старого проекта. Старый JSON не восстанавливается. Сохранение обоих проектов со ссылками на одни пути выдачи может вызвать конфликт артефактов при дальнейшей работе; это требует отдельной проверки.

- [x] В сценарии восстановления сначала проверить историю и текущую ревизию; при необходимости пересоздания явно обозначить новый проект и потерю преемственности истории.
- [x] Проверить индекс проектов и конфликты выдаваемых файлов при двух проектах с одним именем и `overwrite:true`; обеспечить понятную диагностику устаревшего проекта.

## P1. Явно описать единицы толщины и вложенные схемы

В новом логе первый `ppt_create` содержит 20 объектов с `stroke.width` вне диапазона: 18 значений `9525` и 2 значения `19050`. Это значения, характерные для EMU, тогда как `sceneStroke()` принимает пункты в диапазоне 0–100; экспорт умножает толщину на 12700 для записи в DrawingML. Следовательно, 9525 EMU = 0,75 pt, 19050 EMU = 1,5 pt. Замена моделью на 1 и 2 pt проходит проверку, но увеличивает предполагаемую толщину на треть.

Описание `elements` начинается с `Drawing order in original EMU`, а `stroke` раскрыт только как общий `object`. Единицы и ограничения вложенной толщины модель из этой схемы не видит. После замены на 1 и 2 во втором вызове все восемь слайдов из лога проходят `normalizeSceneSlide()` без ошибок.

## Дополнение: P1. Выбор референса при отсутствии purpose:cover

Четвёртый пользовательский лог, получен после реализации первоначального плана. Ошибка: `composition-reference at slides[0]: No reference for this purpose; specify an existing designLayout`. Это отдельный случай, не исправленная ранее сериализация. Во всех восьми входных слайдах отсутствует `designLayout`; первый имеет `purpose:'cover'`, последний — `closing`.

В `composeSceneTemplateSlides()` без явного `designLayout` сначала ищется точное совпадение `purpose`. При отсутствии совпадения для `closing/section` допускается первый `content`, а для `cover` fallback намеренно не выполняется. Значит, запрос обложки без подходящего референса останавливается до генерации файлов. Точные метаданные серверного шаблона в данном фрагменте отсутствуют; утверждение модели «оба варианта content» не является самостоятельным подтверждением.

Локальное воспроизведение на минимальном шаблоне с `layout-1` и `layout-2`, оба `content`: обложка даёт ту же ошибку; closing автоматически выбирает `layout-1`. Добавление только `designLayout:'layout-1'` к первому слайду позволяет нормализовать все восемь слайдов из пользовательского запроса. Это проверка механизма, а не проверка оформления реального шаблона. Утверждение модели, что закрытие также обязательно требует явного ID, не соответствует текущей реализации; ID нужен, если требуется конкретный референс, отличный от автоматического выбора.

- [x] Перед сборкой полного `slides` явно сопоставлять роли с метаданными `ppt_template get`: существующие ID, имена и purpose. Если визуально титульный образец помечен `content`, назначать известный `designLayout`, сохраняя смысловой `purpose:'cover'`; не переименовывать обложку в content только ради обхода ошибки.
- [x] В описание схемы и скилл добавить точные правила: точное purpose; fallback в content только для не-cover; явный designLayout имеет приоритет и может иметь другой purpose. Для оформления закрытия по конкретному образцу указывать его ID.
- [x] Ошибка должна перечислять доступные `{id,name,purpose}`, запрошенный purpose и пример исправления на существующий ID. Не предлагать модели угадать `layout-1` без чтения метаданных.
- [x] Проверить назначение purpose при импорте/создании пользовательского шаблона: визуальная титульная страница не гарантирует семантическую метку cover. Не менять ранее сохранённые шаблоны эвристически и не выбирать первый макет молча для cover.
- [x] Добавить регрессию: только content-референсы + cover без ID; cover с явным существующим ID другого purpose; closing без своего референса; неизвестный явный ID; отсутствие подходящего референса без записи файлов. Проверить разные IDs контентных образцов, чтобы fallback не выглядел как гарантированный выбор нужного оформления.

Статус дополнения: реализовано и проверено локально. `resolveSceneReference()` сохраняет прежние правила выбора и возвращает адресную ошибку со списком доступных ID/имён/ролей и примером явного выбора. `ppt_template get` показывает `defaultReferences`, в том числе null для отсутствующей обложки. Правила добавлены в генерационный промпт, общую схему, скилл и справочник. Проверка реального импорта PPTX подтвердила content по умолчанию; шаблон из scene-проекта сохраняет объявленную роль. Старые шаблоны не изменяются. Четыре новые регрессии проверяют выбор, видимый текст инструмента, отказ до генерации файлов и импорт/создание шаблона.
