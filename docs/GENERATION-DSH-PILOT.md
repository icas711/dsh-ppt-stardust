# Экспериментальный пилот через чат DSH

Тестовая сборка `dsh-ppt@0.20.6-ru.14` добавляет отдельный инструмент `ppt_generation`. Он выполняет контролируемые задания A/B/C через существующий чат DSH: модель получает схему и источники, отвечает через tool call, сервер проверяет ответ, управляет исправлениями и экспортирует файлы. Командная строка и перенос answer.txt для этого пути не нужны.

Это дополнение к этапам 4–5, подготовка живого этапа 6. Обычный `ppt_create` сохраняет прежний путь. Плагин не вызывает модель самостоятельно, не меняет её настройки и не публикует результат. Живой моделью остаётся выбранная в DSH `glm-5.3-flash`.

## После деплоя

Для повторного пилота после исправления карточек использовать сборку `0.20.6-ru.15`. Обновить сервер плагином из подготовленного `.tgz` либо своим обычным способом установки этой сборки, затем перезагрузить плагин/DSH. Проверить фактическую версию `0.20.6-ru.15` и наличие инструмента `ppt_generation`. Дополнительный ключ провайдера или настройка experimental-флага в конфигурации плагина не требуются: разрешение задаётся отдельно при старте явно запрошенного теста.

Выбрать в DSH `glm-5.3-flash`, открыть новый чат и отправить:

> Проведи один экспериментальный запуск dsh-ppt A/B/C: режим A, задание cards, шаблон light. Используй ppt_generation: сначала list, затем start с experimental:true. Выполняй возвращаемые nextRequest через submit до завершения. Не вызывай ppt_create и не запускай другие задания. В конце выдай файлы, предупреждения и журнал этого эксперимента через report. Визуальную приёмку пока не объявляй.

Затем провести B и C с тем же cards/light, каждый в новом чате. Для полного малого пилота следующие группы: chart/dark в порядке B,C,A; long-ru/decor — C,A,B; overload/portrait — A,B,C. Вместе это 12 запусков. Три подтверждающих повторения перспективных сочетаний запускать позже, по результатам пилота и с отдельным новым чатом для каждого повторения.

До генерации уточнить через `ask_user_question` реально недостающие требования и роли вложений. В контролируемом тесте выбор задания/шаблона уже явный, источники назначены содержанием, синтетический шаблон — оформлением; повторять известные ответы без причины не нужно. При необходимости выбора другого оформления/материала согласовать отдельный эксперимент. Этот UI-инструмент пока использует 12 публичных синтетических случаев и четыре шаблона; частный Proekty_II.pptx не импортируется и не объявляется проверенным.

## Протокол инструмента

| operation | Назначение |
| --- | --- |
| list | Доступные caseId, templateKey, режимы и порядок пилота |
| start | `{experimental:true,mode:"A"|"B"|"C",caseId,templateKey}`; возвращает runId, expectedTurn и nextRequest |
| submit | `{runId,expectedTurn,responseText}`; responseText — точная JSON-строка для текущего nextRequest |
| status | `{runId}`; состояние после неопределённого результата или повторного подключения |
| report | `{runId}`; возвращает reportPath с журналом этого чата |

Модель читает `nextRequest.instructions`, `schema`, `sources`, brief/ограничения, затем передаёт JSON через submit. Она не должна выполнять дополнительные команды, перегенерировать задание или исправлять ответ вручную перед сохранением. Ошибочный JSON, включая пустой ответ, сохраняется и расходует попытку. Максимальный размер responseText — 4 MiB. Исправление может требовать `{slides:[...]}` строго для указанных ID; остальные слайды сохраняет сервер.

A — свободная нативная scene-композиция с координатами и стилями, затем прежний экспорт. B — spec одним плановым ответом. C — scenario, затем spec. На всё задание допускаются максимум два исправления: до 3 ответов для A/B и до 4 для C. `expectedTurn` надо брать из ответа сервера, не считать самостоятельно. Сервер не принимает произвольные пути, чужие namespace или IDs шаблонов.

После первого пилота cards/light проверка требует видимого сохранения полной исходной формулировки о равноправии принципов и отсутствии этапов/рейтинга во всех режимах, включая A. Для B/C поддерживается необязательное `visual.caption` у cards — общее пояснение над карточками; точный исходный текст допускается также в видимых `item.detail`. Заметки не заменяют видимый факт. Рубрика допускает дополнительные дословные фрагменты источника, но продолжает отклонять неподтверждённые пояснения, изменения названий, порядка и обязательных деталей. Это детерминированная проверка контролируемого задания, не общая проверка истинности произвольного текста.

Компоненты версии 2 размещают равные по высоте карточки по содержимому, центрируют короткие подписи и значки и сохраняют размер шрифта шаблона. Пояснение учитывается при расчёте доступного места; длинные материалы по-прежнему переносятся на дополнительные слайды только с разрешения brief. Для сравнения с первоначальным пилотом нужен новый запуск: старые ответы и журналы остаются неизменными, новый комплект получает другой хеш входов и кода.

Один эксперимент закрепляется за парой «владелец + ID чата» из доверенного контекста DSH. Повторный start того же задания возвращает прежнее состояние; изменение режима/задания требует нового чата. Новый чат используется для следующего запланированного опыта, не для скрытого повторения неуспешной попытки. Один и тот же submit с тем же expectedTurn/текстом идемпотентен; другой текст для уже занятого хода отклоняется. Параллельные записи защищены межпроцессной арендой файла; во время обработки следует дождаться завершения вызова.

## Сохранность и ограничения измерений

Состояние хранится в `DSH_HOME/plugins/dsh-ppt/generation/<session-hash>/<runId>/`: входной snapshot, точные строки ответов, доверенный маршрут из контекста DSH при его наличии, события и результаты проверок. Недостающие host metadata не восстанавливаются из слов модели. Известный маршрут с другой моделью блокирует start; изменение provider/model во время задания сохраняет полученный ответ и завершает его как route-changed.

Ожидание следующего ответа переживает перезапуск. Если процесс прервался во время обработки/экспорта, статус становится interrupted: бюджет и имеющиеся ответы сохраняются, автоматического повтора экспорта нет. Возможные частично записанные файлы остаются для разбора. При обновлении исходников во время активного эксперимента продолжение отклоняется; сохранять этот исход как незавершённый, новые тесты выполнять на одной закреплённой версии.

Файлы HTML/PPTX/PDF выдаются через тот же механизм, что у обычного `ppt_create`, с постоянным проектом для редактирования и записью в панель презентаций. Папка выдачи разделена по чату и runId. Report копируется в эту папку по явному запросу и может быть скачан через обычные ссылки на файлы DSH. Серверный инструмент возвращает пути; доступность скачивания и рендера на конкретном DSH-сервере проверяется после деплоя.

`responseCapture:"tool-argument"` означает точную строку, переданную моделью в инструмент. Это не полный сырой ответ/транскрипт провайдера: отдельно сохранить историю DSH, сообщения, tool calls и исходные ошибки. Инструмент не имеет достоверных provider usage/billing, поэтому inputTokens/outputTokens/cost остаются null. Не заполнять их самодекларацией модели.

Сервер фиксирует serverStartedAt, firstSubmissionAt, lastSubmissionAt и finishedAt. Они измеряют наблюдаемые границы инструментального протокола, включая серверную обработку; это не точное время первого токена/полного ответа провайдера. Для полного времени от первоначального задания до человеческой приёмки использовать внешний run-журнал и DSH timestamps; время уточнений, холодного импорта/кеша, рендера и просмотра фиксировать отдельно. Локальные trace.jsonl описывают повторную проверку записей и не считаются скоростью модели.

После exported либо ошибки получить report и сохранить outcome. Не исключать незавершённые/неуспешные опыты из сравнения. Технический результат всегда `acceptance:not-verified`. На этапе 6 необходимо открыть/отрендерить итоговые файлы, проверить весь текст, цифры, порядок, геометрию, оформление и нативную редактируемость. Сам по себе exported или отсутствие диагностик не означают человеческую приёмку. Установка этой сборки не является завершённым живым пилотом.
