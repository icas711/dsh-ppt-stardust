# Контракт объектной модели слайда

Дата: 2026-11-19. Результат пакета 1B. Это контракт следующего этапа реализации; текущий плагин ещё сохраняет проекты schemaVersion 1 и шаблоны schemaVersion 1/2.

## 1. Принятые решения

- Следующая версия проекта — `schemaVersion: 2`, шаблона — `schemaVersion: 3`. Версия npm-пакета и версия схемы независимы.
- Слайд новой модели имеет `layout: "scene"`, массив `elements`, необязательные `purpose`, `label`, `notes`, `designLayout`. `label` — имя в интерфейсе, видимый заголовок является текстовым объектом.
- Простой ввод и Markdown остаются публичными способами создания презентаций и преобразуются адаптером. После преобразования рендереры читают только объекты.
- Источник нормализации — чистый `deck-model.mjs`, включаемый в сервер и клиент. Отдельную вручную поддерживаемую исполняемую JSON Schema не заводим: описание аргументов инструментов должно производиться из общего контракта.
- Геометрия — EMU и исходный физический размер страницы. Общая геометрия и преобразования реализуются в `deck-geometry.mjs`.
- Нативные диаграммы создаём через `@office-kit/pptx@0.21.0`; обновляем данные через `setChartSpec`. Собственный ChartML для подтверждённых вариантов не нужен.
- OLE-бинарные части и произвольные исходные ZIP-части не становятся ассетами. Возможны проверенное превью и ограниченные метаданные.

## 3. Матрица текущей поддержки

«Библиотека читает» не означает «импортёр шаблона переносит». «Нативный экспорт» не означает точное воспроизведение любого внешнего файла.

| Объект | Чтение SDK | Импорт шаблона сейчас | Создание / HTML сейчас | PPTX сейчас | Следующий слой работы |
|---|---|---|---|---|---|
| Текст | Текст, абзацы, runs, эффективные стили | Геометрия и стиль первого run; до 6 областей | title/bullets и распределение по областям | Нативные текстовые рамки | Объектная модель, rich text, адресное заполнение |
| Изображение | Байты, рамка, обрезка | Оформление как картинки; контент как область | Одна содержательная image на слайд, несколько картинок оформления | Нативные picture | Несколько независимых image-объектов, crop, порядок |
| Прямоугольная плашка | Геометрия/заливка | Превращается в PNG | Изображение оформления | Picture вместо shape | Нативный shape и отдельный бюджет объектов |
| Иная фигура / линия | API фигур и линий | В основном пропуск | Ограниченные встроенные оформления | Нет общего независимого shape/line-ввода | Типизированные объекты и сериализация |
| Группа | Дерево и transform; есть плоские копии descendants | Обход с пересчётом геометрии, исправлена дедупликация | Нет общей группы объектов | Исходная группировка не восстанавливается | Общая геометрия и семантика группы |
| Обычная таблица | Ячейки и размеры | graphicFrame пропускается | rows, авторазбиение по 8 строк данных, до 8 колонок | Нативная таблица из простого ввода | Независимая table-рамка, сохранение данных и стилей |
| Объединённые ячейки | SDK содержит API spans/merge | Пропуск | Полной модели объединений нет | Генератор не пишет gridSpan/rowSpan | Новая функциональность: модель, HTML, OOXML |
| Column/bar/line/pie | SDK read/write | Пропуск | Есть базовые chart-слайды | Нативный chart и встроенная XLSX | Импорт, несколько chart, передача оформления |
| Doughnut/area/stacking | SDK read/write, подтверждено экспериментом | Пропуск | Продуктовая схема пока не разрешает эти варианты | Низкоуровневое SDK умеет | Расширить общий chart-контракт и HTML |
| OLE | Обёртка/отношения/превью доступны в ZIP | Пропуск | Нет | Нет | Превью/метаданные с явным ограничением; без бинарного переноса |
| SmartArt и специальные объекты | Частичная информация о graphicFrame | Пропуск | Нет | Нет | Отдельная матрица, не обещать поддержку v1 |

### Что именно теряет рабочий пример

В локальном закрытом файле обнаружены 2 кольцевые диаграммы, 1 горизонтальная clustered bar и 1 горизонтальная percentStacked bar, а также 6 OLE-объектов. Исходный контент в этот документ не переносится.

- Отсутствие диаграмм/OLE — ограничение импортёра, а не отсутствие всей необходимой возможности SDK.
- Пропущенные текстовые блоки — лимит областей и недостаточная модель заполнения.
- Переносы и смешанные стили — потери нормализации/модели текста.
- Часть исходных заголовков находится в оформлении макета и пропускается как статический текст.
- Тестовое заполнение пока поддерживает ограниченный набор полей. Его потери фиксируются отдельно от возможностей импортёра; группы обходятся без повторного учёта плоских копий.

## 4. Нативные диаграммы: принятое решение и доказательства

`scripts/probe-pptx-charts.mjs` создаёт 8 диаграмм на двух слайдах, по четыре на каждом: column, bar, line, pie, doughnut, area, stacked-column, percent-stacked-bar.

Эксперимент проверяет:

- Категории, значения и цвета серий после save/load.
- Название и его шрифт, легенду и подписи/числовые форматы.
- Шкалу осей, размер отверстия кольца, тип накопления.
- Наличие отдельной встроенной XLSX для каждого графика.
- Изменение первой серии с `[12, 8]` на `[18, 4]` одновременно в cache и ячейках XLSX.
- Сохранение геометрии при setChartSpec.
- Через WASM: изменение пикселей первого слайда и неизменность второго после правки данных.
- Через локальный PowerPoint: 8 нативных chart-объектов, первая серия `[18, 4]`.

Команды:

```sh
node scripts/probe-pptx-charts.mjs --render
pwsh -NoProfile -File scripts/probe-pptx-charts-native.ps1
node --test test/chart-capabilities.test.mjs
```

Выходы — `.test-output/chart-capabilities/`. Структурный эксперимент включён в обычные тесты, WASM-эксперимент — в задачу CI рендеринга. PowerPoint остаётся отдельной локальной проверкой.

**Решение:** общий chart-контракт адаптируется к API SDK. Подтверждённые свойства не реализуются вторым ChartML-писателем. Прочие возможности — combo, 3D, особые оси, individual labels, внешние связи — требуют отдельных экспериментов. Сам факт наличия поля в d.ts не является критерием поддержки продукта. setChartSpec заменяет встроенную книгу; пользовательское оформление ячеек исходной Excel-книги не обещаем сохранять.

## 5. Схема объектов

Пример будущего нормализованного слайда:

```json
{
  "id": "slide-1",
  "layout": "scene",
  "purpose": "content",
  "label": "Сравнение показателей",
  "designLayout": "variant-1",
  "elements": [
    {
      "id": "heading",
      "type": "text",
      "role": "content",
      "slotId": "heading-slot",
      "frame": { "x": 500000, "y": 300000, "w": 8500000, "h": 600000 },
      "paragraphs": [
        { "runs": [{ "text": "Показатели", "style": { "fontFamily": "Liberation Sans", "size": 24, "bold": true, "color": "#CF1F2F" } }] }
      ]
    }
  ]
}
```

Общие поля: `id`, `type`, `role`, `frame`, необязательные `name`, `slotId`, `transform`, `source`, `support`. Поля зависят от type; неизвестные поля нормализованного объекта отклоняются с путём ошибки. Порядок рисования задаётся массивом elements, отдельный конкурирующий z не вводится.

| type | Содержимое |
|---|---|
| text | paragraphs/runs; явный break, стиль абзаца, textFrame и типографические сведения |
| image | assetId, alt, fit, crop |
| shape | Поддерживаемая геометрия, fill, stroke; ограничения эффектов отражаются в support |
| line | Начало/конец, stroke и стрелки |
| table | Строки/колонки, ячейки с paragraphs, cell spans, поля/границы/заливки |
| chart | Категории, серии, kind, группировка, подписи, оси, легенда и оформление |
| group | children — ссылки на объекты той же сцены; группа сама не рисуется второй раз |
| unsupported | Тип источника, безопасные метаданные, необязательный previewAssetId и причина |

Идентификаторы уникальны в сцене; ссылки на отсутствующие объекты/ассеты — ошибка. Циклы и несколько родителей группы запрещены. Порядок членов группы должен позволять сериализовать её без изменения порядка наложения; несовместимость диагностируется, а не исправляется скрытым перемещением элементов.

### Геометрия групп

frame хранит прямоугольник в EMU. Необязательная affine-матрица `[a,b,c,d,e,f]` отображает его координаты на страницу. Для простого объекта матрица единичная. Для вложенных групп импортёр складывает преобразования в одну итоговую матрицу дочернего объекта; родительский transform не применяется повторно при рендеринге.

Общая функция вычисляет видимые границы по четырём углам и даёт координаты редактору. Логическая группа и исходные transform хранятся раздельно от итогового размещения. Неподдерживаемые для конкретного экспортёра affine-эффекты, например shear, получают явную диагностику/замену по матрице возможностей. Нельзя обещать точность произвольных матриц до проверки обоих экспортёров.

Отрицательные координаты допустимы для частично выходящих за страницу объектов; валидатор не клампит их к нулю. Размеры положительны, числа конечны и находятся в документированном безопасном диапазоне. Непопадание текста в рамку — диагностика вёрстки, а не повод удалить контент.

Пакет 2C: эти расчёты выделены в чистый `deck-geometry.mjs`. Контракт матрицы: `x'=a*x+c*y+e`, `y'=b*x+d*y+f`; `composeTransforms(outer, inner)` сначала применяет inner. `frameTransform` поворачивает по часовой стрелке в градусах вокруг центра рамки, отражение выполняет перед поворотом. `groupTransform` переносит внутренний viewport во внешний с независимыми масштабами, затем применяет отражение/поворот. `transformedBounds` учитывает четыре угла, включая shear и отрицательные координаты. Числа не округляются до сериализации; переполнение и нечисловые значения отклоняются. Нулевые размеры разрешены для вычисления границ линий, но не внутреннего viewport группы. Существующий legacy-импорт использует этот модуль для прежних масштабов/сдвигов, сохраняя свой fallback пустого viewport в 1 EMU. Импорт и экспорт поворотов/отражений ещё не объявляются поддерживаемыми: это требует scene и проверки сериализаторов.

## 6. Ввод и конфликт представлений

Содержательные legacy-поля: `title`, `subtitle`, `text`, `bullets`, `image`, `table`, `chart`, `rows`, `kicker`. Их точный список экспортирует общий модуль.

- Если есть собственное поле elements и любое из перечисленных собственных полей, вернуть `mixed-slide-content`, включая пустые строки, null и пустые массивы.
- Для scene без elements вернуть `missing-elements`; не откатываться на bullets.
- `id`, `label`, `purpose`, `notes`, `designLayout` и разрешённые метаданные могут сосуществовать с elements.
- Смена представления при edit/patch выполняется явной операцией. Нельзя слить patch с существующим legacy-содержимым, а затем молча потерять его.
- Переход из legacy выполняет адаптер: создаёт объекты и удаляет старые поля перед общей валидацией.

Пакет 2D реализует общий контракт `normalizeSceneSlide` / `normalizeSceneSlides` для text, image, shape, line, group и unsupported. Table/chart ещё отклоняются как `unsupported-element-type`: их контракт и сериализаторы вводятся отдельными пакетами. Исходные объекты не изменяются; повторная нормализация даёт тот же результат. Сцена допускает 256 объектов, 128 размещений изображений/превью, 16 уровней групп; документ — 120 сцен и 8192 объекта. Дополнительные текстовые бюджеты одной сцены: 1024 абзаца на объект, 4096 runs и 262144 символа суммарно; один run — до 65536 символов. Рамки содержат целые EMU, координаты ±51206400, размеры 1…51206400 (у линии один размер может быть нулевым). Affine требует шесть конечных коэффициентов, ненулевой determinant, линейные коэффициенты до 1024 по модулю и видимые углы в безопасном диапазоне EMU. Эти пределы не заменяют проверку выхода за физическую страницу.

Валидатор проверяет ID, существование дочерних объектов, единственного родителя, циклы и непрерывный порядок рисования членов группы. Transform родителя повторно к детям не применяется. Image/preview ссылается только на существующий PNG/JPEG-ассет; проверка байтов ассета остаётся ответственностью файлового слоя. Произвольные поля, включая бинарные части OLE, отклоняются. Ошибки содержат `code` и `path`, одинаковые в Node и собранном браузерном коде. `scripts/bundle-client-model.mjs` обходит явный граф локальных ES-модулей, включая геометрию; внешние/динамические импорты, циклы и выход из каталога запрещены.

Производственный legacy-путь пока не принимает scene: `assertLegacySlideInput` сначала выдаёт `mixed-slide-content` / `missing-elements`, а для отдельной сцены — `scene-not-enabled`. Защита применяется к созданию, preview, чтению текущего состояния/истории и объединённому patch до записи файлов. Это промежуточный контракт для адаптера и миграций, а не объявление готовности проекта v2 или шаблона v3. Проверки пакета: 361 тест, исходный нативный golden и шесть синтетических рендеров без регрессий.

## 7. Шаблоны и миграция

Шаблон v3 содержит существующие семейства/варианты, но оформление представлено elements, а области нового контента — slots с id, ролью, допустимыми типами, обязательностью и ограничениями. Содержательные данные не становятся фиксированными объектами оформления автоматически.

Старые images преобразуются в image-элементы оформления, textZones — в slots с устойчивыми идентификаторами. Одновременный старый и новый формат одного варианта отклоняется ошибкой `mixed-template-layout`. Заполнение — по slotId, не по порядку bullets. Смена структуры сопоставляет области по стабильным ролям/идентификаторам; несопоставленный контент остаётся в диагностике и не удаляется.

Миграция проекта:

1. Прочитать исходный файл, сохранить fingerprint и проверить исходную версию.
2. Преобразовать текущие slides и все snapshots истории в памяти, сохранив deckId, slide.id, revision, ссылки на ассеты, заметки, dataModel и происхождение.
3. Идентификаторы объектов адаптера выводить детерминированно из slide.id, роли и индекса. Чтение/undo не должны генерировать каждый раз новые объекты.
4. Проверить нормализованную сцену и историю общим модулем.
5. При реальном сохранении записать v2 обычным атомарным путём с проверкой revision/fingerprint. Само чтение не меняет файлы и revision.

Старый клиент уже отклоняет неизвестную schemaVersion проекта; это поведение сохранить для защиты v2. Экспорт обратно в v1 не поддерживать с потерями: отдельная операция возможна только для полностью представимых сцен, иначе `legacy-export-unsupported`.

Связи dataModel и вычисляемые значения сохраняются как явные dataBinding отдельно от slotId шаблона. Перед статическим PPTX-экспортом вычисляются подтверждённые значения; исходные метрики/assumptions/lineage остаются в проекте и заметках по текущему контракту. Их нельзя потерять при простом преобразовании текста в объекты.

Пакет 2E выделяет подготовку структуры прежнего проекта в `deck-migrations.mjs`; это ещё не преобразование содержимого в scene. `normalizeLegacyProjectEnvelope` работает с копией в памяти и сохраняет текущую schemaVersion (включая отсутствие версии), deckId, revision, данные/ассеты и все snapshots. Если в исходном JSON нет deckId, используется `legacy-` плюс первые 32 символа SHA-256 исходных байтов; fingerprint передаёт файловый слой. Отсутствующие ID слайдов задаются как `legacy-slide-N` с детерминированным суффиксом при конфликте с уже существующим ID. Это обеспечивает стабильность повторного чтения одной и той же старой версии. Для анонимных слайдов без исходной идентичности связь разных исторических состояний сверх этой позиционной конвенции не восстанавливается.

Все имеющиеся ID сохраняются. Дубли и нестроковые ID проверяются отдельно в текущем состоянии и каждом snapshot; неизвестная версия проекта/состояния явно отклоняется. Чтение не меняет файл, mtime, revision или dataModel fingerprint. Новая запись по-прежнему использует schemaVersion 1, атомарный commit, исходный fingerprint и проверку expectedRevision; переполнение revision отклоняется до генерации. Тест проверяет путь старого JSON без ID через повторное чтение, отдельную копию, изменение по ID и undo, сохраняя исходные байты. 365 тестов и обе golden-проверки прошли без регрессий. Преобразование legacy-содержимого в scene и версии проекта 2 / шаблона 3 остаются следующими пакетами.

## 8. Бюджеты первой объектной версии

Измерения — `node --expose-gc scripts/benchmark-pptx-import.mjs --render`. Прогон фиксирует исходные объекты, размер полной простой проекции, текущего обрезанного шаблона, уникальные ассеты, время чтения/импорта, heap delta и время исходного WASM-рендера.

Локальные наблюдения до рендера, Windows/Node 22.19.0:

| Содержимое | Исходных объектов | Простая проекция JSON | Импорт, мс | Heap delta, МиБ |
|---|---:|---:|---:|---:|
| 10 блоков + заголовок | 11 | 1 126 Б | 57 | 2,44 |
| 30 блоков + заголовок | 31 | 3 154 Б | 41 | 3,33 |
| 100 блоков + заголовок | 101 | 10 199 Б | 74 | 4,60 |
| 256 блоков + заголовок | 257 | 26 245 Б | 171 | 12,48 |
| 128 размещений одного логотипа + заголовок | 129 | 12 509 Б | 16 | 11,50 |
| 100 блоков + 30 логотипов + заголовок | 131 | 13 105 Б | 68 | 5,55 |
| 10 блоков + 16 групп + заголовок | 27 | 2 486 Б | 14 | 9,49 |

Это наблюдения одного прогона, не SLA и не peak memory. Первый случай включает прогрев. Текущий импортёр всё ещё обрезает до 6 областей/12 изображений; полная простая проекция не содержит всей будущей rich-модели. Повторные результаты и renderMs находятся в `.test-output/import-capacity/report.json`.

Зафиксировать стартовые ограничения для реализации v2/v3:

| Бюджет | Решение |
|---|---|
| Все объекты одной сцены | 256, включая оформление, группы и неподдерживаемые объекты |
| Размещения изображений/превью | 128 в рамках общего бюджета 256; shape/line/chart/table не расходуют этот счётчик |
| Глубина групп | 16 |
| Все объекты проекта / библиотеки вариантов одного шаблона | 8192; переиспользуемый вариант считается один раз в шаблоне, его размещения — по сценам в проекте |
| Слайды / варианты | Сохранить 120; другие бюджеты могут ограничить документ раньше |
| Один image / images шаблона / images проекта | Сохранить 5 / 8 / 32 МиБ |
| Manifest шаблона / JSON проекта с историей | Сохранить 1 / 64 МиБ до замеров реальной rich-модели |
| Fonts | Сохранить 12 МиБ на файл / 32 МиБ суммарно |
| ZIP шаблона: вход / распакованные части | Сохранить 64 / 64 МиБ; не смешивать с лимитом images |

256 — лимит всех объектов, поэтому пример с 256 блоками и заголовком содержит 257 и должен явно отклоняться новым валидатором. Пример 100+30 укладывается. 128 размещений одного логотипа используют один уникальный ассет 102 Б; 128 больших фотографий не обещаем вместить в 8 МиБ.

Эти значения становятся кодом только в пакете 2. Нужны граничные тесты 256/257, 128/129, 16/17, 8192/8193 и точные байтовые границы. Валидация входа отклоняет превышение с путём и числом объектов. Импорт возвращает неполный результат и подробную диагностику; полный импорт при жёстком превышении не объявляется успешным. Общий модуль задаёт одинаковые числа и коды для клиента/сервера.

История проекта валидируется отдельно в каждом snapshot; её байты входят в общий размер JSON. Нельзя разрешить обход числа объектов через группы или каждый раз считать один ассет несколько раз по его размещениям. Более высокие лимиты и JSON manifest обсуждаются после замеров реальных объектов и обоих рендереров.

## 9. Границы модулей и следующий пакет

- `deck-model.mjs`: версия, типы, нормализация, ограничения и ошибки; без Node/DOM/внешних импортов.
- `deck-legacy.mjs`: прежний ввод и Markdown → объекты, с сохранением поведения старых проектов.
- `deck-migrations.mjs`: преобразования сохранённых схем и истории, без скрытой записи файлов.
- `deck-geometry.mjs`: EMU, affine, границы и группы, чистые функции.
- `deck-html.mjs`, `deck-pptx.mjs`: сериализация одного нормализованного представления.
- `deck-core.mjs`: совместимые публичные входы и координация.
- `build-client.mjs`: включение того же исходника модели перед панелями. Проверять паритет нормализации, ошибок и лимитов с сервером.

Рефакторинг сначала выделяет прежние функции без изменения результатов и проходит существующие тесты/эталоны. Затем включаются новая схема и адаптер. Ни новая версия документа, ни элементы не объявляются поддерживаемыми продуктом до прохождения чтения, сохранения, undo, шаблонов, HTML, PPTX и проверок клиентского паритета.

Пакет 2A: общий `deck-model.mjs` уже используется для существующих textZones, стилей текста, рамок, цветов и сведений о шрифтах. `deck-fonts.mjs` и `deck-text-slots.mjs` сохраняют совместимые экспорты; сервер и клиент обращаются к одному исходнику. Сборка отклоняет неожиданные импорты/реэкспорты общего модуля, а тест сравнивает его Node-экспорты с кодом, реально включённым в `lib/client.js`. Это первый шаг рефакторинга, не включение схем v2/v3.

Пакет 2B: прежние Markdown и нормализация slides перенесены в `deck-legacy.mjs`, сериализаторы — в `deck-html.mjs` и `deck-pptx.mjs`. Общие зависимости выделены в `deck-language.mjs`, `deck-text.mjs`, `deck-theme.mjs`; соответствие фоновых типов находится в существующем `deck-page.mjs`. Модули не импортируют `deck-core.mjs` обратно. Совместимый вход уменьшился с 2604 до 340 строк и сохраняет 31 публичный экспорт. Проверены 349 тестов, исходный нативный golden test, шесть синтетических рендеров и прямое сравнение с предыдущей реализацией на 20 сочетаниях тем/языков: нормализация одинакова, HTML/PPTX побайтово совпадают. Адаптация старого содержимого к scene, новая геометрия и миграции ещё не включены.

Пакет 2F подключает scene к низкоуровневым `renderHtml` и `buildPptx` через `deck-scene-html.mjs` / `deck-scene-pptx.mjs`. Это рендер нормализованного manifest в памяти; файловые операции проекта и инструменты пока сохраняют legacy-защиту до завершения миграции. Исходные EMU не масштабируются повторно под 16:9. Rich text сохраняет отдельные runs, разрывы, абзацные стили, поля и anchor; в PPTX это нативные текстовые рамки. Shape/line — нативные фигуры и коннекторы. Crop и fit вычисляются одинаково для HTML и PPTX; повторные размещения одного изображения переиспользуют одну media-part во всей презентации. Бинарные OLE-части не читаются и не копируются. Unsupported без превью получает видимую рамку с причиной, а не молчаливый пропуск.

HTML использует SVG и foreignObject для текста. PPTX принимает affine с независимыми масштабами, поворотом и отражением; shear явно отклоняется с `scene-transform-unsupported`. Группы пока семантические: рисуются только дети с итоговым размещением, исходные grpSp-контейнеры не восстанавливаются. Точные различия HTML-типографики и dash/стрелок требуют отдельного браузерного рендера; PPTX golden не доказывает их пиксельный паритет. Table/chart ещё не включены в scene-контракт.

`scripts/golden-pptx-scenes.mjs` сравнивает пять независимо написанных OOXML-исходников с полной scene-проекцией, включая 13 текстовых блоков, смешанные стили, вложенные группы, 13 логотипов и линию, порядок фигур. Нельзя заменить эталон для прохождения этого теста: порог source vs actual ≥ 0,999 проверяется по всей странице и каждой видимой области. Пакет включён в `test:pptx-render` и существующую CI-матрицу Linux/Windows; локальный WASM-прогон дал SSIM 1,000000 во всех пяти случаях. Это отдельный путь от пока ограниченного импорта шаблонов. Сохранены также прежние regression baselines и нативный golden; 373 теста прошли.
