# Ручной комплект компактной генерации A/B/C

Этап 5 плана `docs/FEATURE-PLAN-COMPACT-GENERATION-2026-11-20.md`. Подготовка и проверка работают локально, без вызовов модели. Целевая модель живого эксперимента — `glm-5.3-flash`; запускать её предстоит оператору в DSH на этапе 6. Production `ppt_create` не переключается на экспериментальный путь.

Если доступен только чат/UI сервера DSH, используйте [пилот через `ppt_generation`](GENERATION-DSH-PILOT.md) в тестовой сборке `0.20.6-ru.14`. Описанный ниже файловый комплект остаётся отдельным локальным способом запуска.

## Подготовка

Команды выполнять из репозитория плагина. Выбирать новую или пустую папку; исходники оценщика и генератора после подготовки комплекта закреплены хешем. При изменении кода подготовить новый комплект.

```powershell
node scripts/generation-evaluation.mjs prepare-compact .test-output/compact-generation-kit
```

Создаются 12 независимых заданий, четыре ZIP-шаблона v3 с preflight/профилями, реестры источников и ассетов, готовые промпты A/B/C, JSON Schema, расписание и формы журналов. Эталоны не включаются в модельные промпты: `review/rubrics.json` предназначен только для оценщика.

| Задания | Что проверяется |
| --- | --- |
| process, cards, chart, timeline | Порядок, равноправные элементы, числа/единицы/категории, даты |
| comparison, big_number, table, image | Общие критерии и null, число с пояснением, сетка данных, внешний assetId |
| long-ru | Полные русские предложения без сокращений; разрешено увеличение числа страниц |
| incomplete | Неизвестные значения сохраняются явно, без домыслов |
| invalid-chart | Отклонение ошибочного предложения pie; категории и значения не нормализуются |
| overload | Все 30 строк реестра сохраняются при разбиении, заголовки повторяются |

Все публичные материалы — синтетические, источники имеют `synthetic:true`, презентации создаются в `demo` с видимой маркировкой. Шаблоны: светлый, тёмный, с выраженным правым декором и портретный 7559675 × 10691813 EMU; обычные страницы 12192000 × 6858000 EMU. Принудительного 16:9 нет. Шрифты — Arial, фактическую доступность и подстановки нужно записать при рендеринге.

`schedule.json` содержит 12 пилотных запусков: cards/light, chart/dark, long-ru/decor, overload/portrait, по A/B/C для каждого. Затем предусмотрено три повторения каждого из 48 сочетаний задания и шаблона: 432 записи confirmation. Это расписание, а не автоматический запуск 444 запросов. После пилота выбирать перспективные режимы и сопоставимые задания, записывать причину пропуска остальных и заранее задавать порог ускорения. Результаты не удалять из расписания. Порядок A/B/C чередуется между заданиями и повторениями.

## Самостоятельный запуск в DSH

1. Выбрать строку pilot в `schedule.json`. Для каждого run использовать новый чат DSH и отдельную рабочую папку. Не переносить память, ответы или исправления из другого режима. Внутри одной тройки использовать одну модель, провайдера, материалы, шаблон, требования и права на увеличение числа слайдов.
2. Заполнить `runs/RUN_ID/run.json`: фактические DSH/provider/model/installedPlugin, условия кеша и scope. `versions.plugin` — версия экспортера из комплекта, `installedPlugin` — фактически используемая версия; несовпадение исключает приёмку сравнения. Холодный импорт и повторный доступ помечать фактически, не угадывать. Отдельно записывать время уточнений, чтения шаблона, импорта и построения профиля. Если данных нет — null/unknown.
3. Открыть `tasks/TASK_ID/A.md`, `B.md` или `C.md`. Это готовый начальный промпт с brief, schema, профилем и исходными фрагментами. Для image приложить файл из `assetFiles` в `request.json`; PNG/JPEG уже лежит в подпапке assets. Модель возвращает только assetId, без base64. Не передавать ей review/rubrics.json.
4. До первой генерации уточнить через реальный DSH `ask_user_question` недостающие цель, аудиторию, язык, подробность, роли вложений, шаблон, число слайдов и обязательные факты. В контролируемых заданиях оператор уже назначает sources содержанием и выбранный template оформлением; заполненные ответы не спрашивать повторно. Новые частные вложения без установленной роли сначала уточнить. Сохранить настоящий tool history и время разговора отдельно. Самодекларация модели не является подтверждением вызова инструмента.
5. Сохранить точный ответ модели в локальный `answer.txt`, не удаляя ошибки, Markdown fences или иные части. Добавить его в журнал командой ниже. Она сама определит stage/kind, сохранит исходный текст как JSON-строку без необходимости ручного экранирования. Альтернатива — аккуратно дописывать `responses.json`, сохраняя прежние записи неизменными.

```powershell
node scripts/generation-evaluation.mjs record-compact .test-output/compact-generation-kit RUN_ID answer.txt
node scripts/generation-evaluation.mjs advance-compact .test-output/compact-generation-kit RUN_ID
```

6. Если результат `waiting-for-response`, открыть возвращённый `nextPrompt` и передать этот файл в тот же DSH-чат. Он содержит точный следующий запрос: scenario → spec или адресное исправление. Сохранить следующий ответ новым файлом, затем повторить record/advance. У A стадия `scene`, у B — `spec`, у C — `scenario`, затем `spec`. A/B имеют один плановый вызов и максимум два исправления; C — два плановых вызова и максимум два исправления суммарно, без сброса бюджета. Ошибка формата исправления тоже расходует попытку.
7. Продолжать до `exported` или честного терминального сбоя. Не начинать то же задание заново ради обхода лимита. Сбой до первого ответа записать в run.json с фактическим статусом, generationStartedAt и limitations; его строка остаётся в отчёте. Ошибку транспорта во время шага можно записать как response `{error:"точный текст ошибки",stage,kind}`. Модель не переписывает содержание ради ремонта геометрии или импортера.

Начальные промпты и последующие запросы составляют один протокол; сценарий и ответы других режимов не передаются между чатами. Локальные команды не вызывают модель. A использует свободные scene-объекты с координатами/стилями и существующий `templateCreateOptions`/экспорт. B/C проходят `generation-spec-v1`, детерминированные компоненты и тот же экспорт. Старый `deckPlan` не является входом новой проверки. Предусмотренный A формат JSON служит оболочкой для фиксации свободной scene-композиции, production-интерфейс не меняется.

Каждый advance создаёт новую папку `attempts/NNNN`: снимки responses/run-input, последовательный JSONL, result и при необходимости next-request/next-prompt. При успехе артефакты лежат в deck. Предыдущие ответы, результаты и журналы проверяются по SHA-256 и не перезаписываются. После терминального исхода добавление попыток прекращается. Хеши обнаруживают изменение сохранённых данных; они не являются цифровой подписью и не доказывают происхождение ответа от провайдера.

## Ответы, usage и время

Формат `responses.json`:

```json
{
  "version": 1,
  "responses": [
    {
      "stage": "spec",
      "kind": "initial",
      "text": "точный исходный ответ модели как строка",
      "provider": "фактический провайдер",
      "model": "glm-5.3-flash"
    }
  ]
}
```

Для сохранения metadata вместе с новым ответом:

```powershell
node scripts/generation-evaluation.mjs record-compact KIT_DIRECTORY RUN_ID answer.txt metadata.json
```

Допустимы provider, model, error, usageOrigin и usage. Токены/стоимость агрегируются только при `usageOrigin:"provider"` и наличии подтверждённых провайдером значений. Нормализованная форма usage: `{inputTokens:integer,outputTokens:integer,cost?:{amount:number,currency:string}}`. Сохранить исходную квитанцию/метаданные провайдера отдельно, если нормализовали названия полей. Не подставлять примерные значения или длину текста. Если хотя бы для одного обращения данные отсутствуют, общие токены/стоимость — null, а покрытие callsCovered показывается отдельно. Разные валюты не складываются.

В run.json записать ISO timestamps с timezone: `generationStartedAt`, `firstResponseAt`, `finishedAt`, `acceptedAt`. Главное время — от начала первой генерации до пользовательской приёмки, включая исправления и проверки; время уточнений и подготовки шаблона хранится отдельно. `firstResponseAt` означает получение полного первого ответа. Журнальное время локального replay не используется как скорость модели. Для незавершённого задания acceptedAt остаётся null; для сбоя finishedAt фиксирует фактическое завершение попытки.

`cache.condition` допускает cold/repeated; неизвестное условие оставлять null и указать причину. `cache.scope` обозначает фактический изолированный контекст кеша. Повторный импорт в другом процессе не считать попаданием в кеш без свидетельства. Формы содержат manualInterventions и limitations: перечислять ручные изменения и недоступные проверки, не прятать их в успешном статусе.

## Приёмка человеком и оценщик

После `exported` отрендерить итоговый PPTX доступным `ppt_render` либо другим зафиксированным рендерером. Открыть файлы, просмотреть все страницы, проверить источники и редактируемость в целевом приложении. Артефакты, рендеры, сведения о версии рендерера и подстановках шрифтов сохранить в папке запуска. Отсутствующий рендерер или PowerPoint/LibreOffice не заменять утверждением об успехе.

`human-review.json` заполняет человек. Указать reviewer, reviewedAt, artifactSetSha256 из результата последнего advance, renderEvidence и шесть checks. Пример формы свидетельств рендера:

```json
{
  "renderEvidence": [
    {"path":"renders/slide-1.png","sha256":"фактический SHA-256 файла"}
  ]
}
```

Пути — относительно `runs/RUN_ID`, для PNG/PDF проверяются существование, сигнатура и хеш. Это контроль сохранности файлов, не доказательство визуального качества или покрытия всех страниц. Человек подтверждает факты, открытие файлов, отсутствие критической обрезки/перекрытий, читаемость, оформление шаблона и нативную редактируемость. Не ставить true до проверки; отзывы модели сами по себе не дают приёмки. Отзыв привязан к конкретному набору артефактов: после изменения файлов нужен новый запуск и просмотр.

```powershell
node scripts/generation-evaluation.mjs review-compact .test-output/compact-generation-kit .test-output/compact-generation-review
```

Отчёт сохраняет все 444 запланированные строки, в том числе not-run, сбои до ответа, исчерпание бюджета и непроверенные экспорты. `technicalPassed` означает успешную повторную проверку точных ответов, нового контракта/scene, композиции и сохранности HTML/PPTX. `accepted` дополнительно требует относящегося к артефактам отзыва человека, рендера, версий, условий кеша и упорядоченных живых timestamps. Технический результат advance всегда имеет `acceptance:not-verified`.

Контролируемая рубрика проверяет заданные дословные факты, числа/единицы/даты/порядок/null и соответствие данных. B/C проверяются по spec до размещения. Для A читаются видимые подписи scene и нативные chart/table/image; подмена ассоциаций диаграммы/сетки таблицы обнаруживается отдельно. Название единственной серии может храниться в редактируемых данных без отдельной легенды. Произвольное перефразирование, истинность частных материалов, смысл стрелок и общий визуальный результат требуют человеческого просмотра. Отсутствие замечаний рубрики не является универсальной семантической проверкой.

Медиана и диапазон времени считаются только для принятых результатов внутри одного задания, шаблона, режима, фазы, условий кеша и записанного маршрута/версий. Количество непринятых, незавершённых и пропущенных запусков сохраняется рядом; их не превращают в быстрые успехи. `winner` всегда null на этом этапе. Для решения нужны живой пилот, минимум три сопоставимых повторения перспективных вариантов и анализ разброса на этапах 6–7. `allAttemptedAccepted` не означает, что выполнен весь план; для этого существует отдельное поле complete.

CLI review завершается кодом 0 только если есть попытки и все начатые задания приняты; иначе 1, сохраняя отчёт. Подготовка и ожидание следующего ответа не считаются приёмкой. Папка отчёта также должна быть новой или пустой.

## Частные материалы

Сам пользовательский `Proekty_II.pptx` в рабочей папке отсутствует и в публичные fixtures не добавлен. Его роль автоматически не назначается. Для включения материала заполнить локально `private-case.example.json` из комплекта: уточнить роли исходных вложений, подготовить brief, реестр фрагментов и requiredTexts, при необходимости content-ассеты. Затем:

```powershell
node scripts/generation-evaluation.mjs prepare-compact NEW_KIT_DIRECTORY PRIVATE_CASE_JSON
```

Добавленный private-case попадёт во все четыре шаблона и подтверждающее расписание; значения копируются только в указанную локальную папку. `dataMode` по умолчанию factual; синтетические источники требуют demo. Для частного материала проверяются заданные буквальные факты и общий контракт, полный смысл проверяет человек. ZIP/PPTX пользовательских шаблонов уже поддержаны отдельным runner этапа 4; сравнение нового пользовательского оформления следует вести отдельным согласованным набором с сохранением preflight и ограничений импорта.

Живые ответы, материалы и журналы могут содержать частные сведения. Хранить локальный комплект с теми же правами, что и исходные материалы, и не добавлять его в публичные fixtures. `.test-output/` исключён из Git. Этот этап не публикует файлы и не устанавливает плагин в DSH.
