# dsh-ppt

Turn one sentence or a document into a complete presentation: **standalone HTML web slideshow + editable PPTX**. This file handles routing and rules only; read `references/` on demand for specific guidelines.

## Trigger Conditions

The user wants to create a PPT / slides / presentation / deck / report / proposal / pitch deck / roadshow / training materials, or wants to turn a single sentence, a snippet of text, or a Markdown file into a playable presentation.

## Explicit experimental A/B/C pilot

Only when the user explicitly asks for the experimental A/B/C pilot, use `ppt_generation` instead of the normal creation pipeline below. This is a separate controlled-demo protocol, not the default presentation workflow. The current DSH chat model must be `glm-5.3-flash`; the tool does not call or switch models.

- Call `ppt_generation {operation:"list"}` to see case IDs, templates and pilot order. For a specified test, call `{operation:"start",experimental:true,mode:"A"|"B"|"C",caseId,templateKey}`. One experiment per fresh DSH chat; run only the requested experiment.
- Follow the returned `nextRequest` schema, instructions and external sources. Generate its strict JSON and immediately submit that exact text through `ppt_generation {operation:"submit",runId,expectedTurn,responseText}`. The tool handles validation, native composition and export. Do not call `ppt_create`, run shell scripts, create answer.txt or ask the user to transfer JSON files for this UI path.
- Use each returned `expectedTurn` exactly. Continue only on `waiting-for-response`. C first produces scenario, then spec; at most two corrections are shared by the entire task. Bad responses stay in the journal. A terminal failure must be reported; starting over or changing mode in the same chat cannot reset the limit. After transport uncertainty use `status`; if the first `start` response was lost, omit `runId` to recover the active run in this chat. An identical resubmission is idempotent.
- Sources are explicitly demo content and the chosen synthetic template is explicitly style. Clarify genuinely missing requirements/attachment roles via `ask_user_question`; do not repeat supplied answers. The tool cannot verify DSH question history. New private materials are outside this controlled UI pilot; never claim they were tested.
- On export deliver the returned HTML/PPTX/PDF and relevant warnings. `report` exports this experiment's log for the pilot; include it when requested. Both `status` and `report` may omit `runId` to use the active run in this chat; `submit` requires the returned `runId`. State `acceptance:not-verified`: render, factual/visual inspection and editability need human review. Provider usage is unavailable; never fill token/cost values from self-report. The saved response is the submitted tool argument, not the complete raw model/provider transcript.

## Execution Rules (Must Always Be Followed)

- Default workflow: clarify, prepare content, create, deliver the returned files and relevant warnings. The plugin already validates inputs, saves and revision conflicts internally. A successful operation does not require a separate ppt_check, render, image inspection, pixel/metric script or repair loop. Warnings alone are advisory, not permission to change content, fonts or geometry. Fix a concrete blocking error within the agreed task, or a defect the user asked to fix; do not start an autonomous quality-improvement cycle. Extended visual/metric review is opt-in and limited to the user's requested scope.
- Deliver the final output directly by default without automatically triggering AI pre-review or defense/rehearsal modes. Users can manually enable these two optional modes in the download section of the settings page, selecting the model, scope, and call limit before submitting materials. AI rehearsal does not substitute for fact-checking—never fabricate experiments, data, or citations; save adopted suggestions as a new copy while keeping the original intact.
- When the user needs AI visual inspection, they can manually enable it via DSH Settings → Presentation → Visual Inspection & Repair. This requires a vision-capable model and the official rendering engine; repairs only adjust layout, save as a new copy, and re-verify. The absence of AI-detected issues does not equal human sign-off; any model call failures, output truncations, interruptions, or uninspected slides must be explicitly reported—never claim visual inspection passed if it did not.
- If image viewing is unavailable for the current model, or `read_image` fails with an adapter/provider error (for example `no adapter registered for provider`), stop attempts at AI visual inspection and immediately tell the user: «Презентация создана, но я не смог визуально проверить слайды: просмотр изображений в текущей конфигурации недоступен. Пожалуйста, проверьте все страницы в PPTX, PDF или HTML самостоятельно». Adapt the file list to files actually created; if only some pages were inspected, state which remain unchecked. Use the structural results already available and deliver the existing artifacts with `visual:not-verified`. Do not automatically delegate to a subagent, select/configure another provider/model, or trigger review-role setup as a workaround. A separate AI review requires an explicit user request; inability to inspect images must not block delivery or be represented as visual approval. In a requested review, establish that image viewing works on one page before queueing other pages; after a provider/adapter failure do not retry each page. Use only exact pngPaths/receiptPath returned by ppt_render; never scan shared directories to find them.
- Enable numerical traceability and live simulation on demand. Provide `dataModel` and structured `slides` with `{{metricId}}` bindings; read `references/data.md` first. Source facts must correspond to actual rows or cells in the source material; mark user assumptions with `kind:input`, and never fabricate sources. To modify data, run `ppt_data(action:preview)` first, display the metric and slide diffs, and save only after receiving confirmation along with the original preview token and revision number (saving as a new copy by default). Offline HTML parameters must be saved back and confirmed before delivering the corresponding static PPTX.

- Use the exact revision returned by the latest successful create/edit/undo. Never guess or intentionally provoke a conflict to discover it. Read `ppt_check` only when revision or target object data is missing, state may have changed, or a real error needs diagnosis. Reading the target slide for an edit is not a request for a full quality audit. Externally edited HTML/PPTX files or legacy projects lacking a build verification record must not be overwritten; inform the user that `saveAs:true` saves a new copy solely from the JSON source while keeping the original intact, and manual edits made in Office will not be imported. Never bypass verification or manually tamper with checksums.

- Give each slide a clear main idea supported by useful detail, facts and evidence. One idea does not mean one phrase; compose several blocks when useful.
- Write the content in the language you author; `lang` only controls the UI text. Always set `lang` explicitly to match the user's conversation language — `ru` is fully supported (player UI, presenter window, PPTX kickers, ru-RU number format), as are `zh`, `en`, and `bilingual`.
- **Обязательно: используй ask_user_question и задавай вопросы пока задача не будет ясна.** After receiving inputs for EVERY new deck, call DSH `ask_user_question` and wait for answers before generation. Confirm the template even if already specified; if none are installed, clarify the visual style. Ask about content: objective, audience, key facts, missing materials, depth and slide count. Group questions and continue until material ambiguities are resolved. Never skip this for short or complete requests. If the tool is unavailable or unanswered, explain the blocker and stop before generation. Do not silently choose a template or style.
- Before asking for template choice, call `ppt_template list`. Offer **every returned template**, including all personal (`user:`) templates, with its actual name and exact key. Recommendations may change the order, never the completeness. Do not filter by perceived suitability or replace a listed template with a custom-style option. If tool option limits prevent one complete question, split the list across questions or ask for a group first and then show every entry in that group. Only an empty list leads to a style-only question. Current tool results take precedence over remembered template availability.
- After clarification, inspect the selected installed template with `ppt_template get`. Preserve its page size, fonts, colours and fixed artwork. A cover and a content reference are enough: freely compose multiple text blocks, shapes, diagrams, tables and charts on content slides. Existing variants are references, not a required catalogue or a limit on content density. With no installed templates, use the confirmed style through `brand` and `slides` without `templateId`.
- Use the delivery checklist below with information already available; it does not require extra tool calls.
- Aim for a production-ready deliverable: organize real content first before calling the generator; any unfilled templates must be explicitly marked as drafts—never fabricate missing facts.
- Report missing-font warnings when available. Do not automatically substitute a template font, shorten text or resize objects to clear warnings. Preserve the agreed design and content; changes require a concrete task-related defect or the user's request. Never claim visual verification without an actual inspection.

## Core Pipeline

1. **Probe Requirements**: Read the input, then use `ask_user_question` to confirm template/style and clarify content. Wait for answers; repeat while material questions remain.
2. **Outline**: Preserve the requested slide count and sequence. A one-slide task means one slide, with no extra cover or closing. When the count is unspecified, propose a concise outline suited to the material; add cover/closing only when useful.
   → Read `references/copywriting.md` before writing the outline and body copy.
3. **Select Template**: After confirming template/style through `ask_user_question`, inspect the selected `templateId` with `ppt_template get`, or use the agreed style when the library is empty. Only actually listed builtin/public/user keys are available. An error loading the selected template requires resolving that error; do not silently switch templates.
   → Read `references/templates.md` for template keys, outline skeletons, and per-slide `layoutId`.
4. **Build**:
   - For a table-only deck with an agreed schema 3 library template, use `ppt_create` with `title`, `templateId`, `lang` and `tableSpec` instead of hand-written scene geometry. `tableSpec` is `{version:1,mode:'factual'|'demo',sources:[{id,text,synthetic?}],tables:[{id,title,sourceRefs,headers,rows,notes?,designLayout?}],allowMoreSlides:boolean,contentHash?:string}`. Copy rows/cells verbatim from the supplied material; null means unknown, not zero. Before treating a DOCX cell as empty, resolve automatic list numbering (numPr/numbering.xml), fields and footnotes: absence of w:t text is not proof of a blank visible cell. Preserve displayed numbering and its restarts; record footnotes in notes with their cell association. If numbering cannot be resolved, disclose that limit rather than silently emitting null. Keep one logical table per source register (up to 8 columns, 30 rows per logical table), with no artificial cover or summary rows. When additional pages are allowed, set `allowMoreSlides:true`: the engine preserves the template and automatically repeats headers while paginating rows; an oversized row continues on labeled slides without shortening text or shrinking fonts. Exhausted cells are blank on continuation pages; unknown values appear as em dashes in the first fragment. If the user fixed the page count, do not enable extra pages without agreement. Preserve a supplied contentHash when copying a verified JSON request; a mismatch must stop generation, never remove or recompute the hash to accept altered text. Brief requirements and pagination instructions are not table content. Do not combine this input with content/slides/deckPlan, dataModel or style overrides. This is the ordinary creation tool: no experiment, fixed model, caseId, scenario, start or submit is needed. For larger registers, mixed decks or other template schemas, use the existing content/scene path and preserve all data. See `references/table-create.md` for the full limits and example.
   - Inside DSH: Call `ppt_create` with the chosen `templateId`, for schema 3 normally use `templateId` + freely composed `slides` with `layout:'scene'` and `elements`. The engine adds fixed artwork and typography; no `deckPlan` or `validate-plan` is needed. For legacy templates use Markdown `content` or structured `slides`.
   - Cross-harness: Run `node <skill-dir>/scripts/build-deck.mjs --title "Title" --content deck.md --template-file <bundle.zip> --lang en --out dist` (there is no template library — export a bundle first; `--theme` is a legacy fallback).
   - Motion is enabled by default (slide transitions + sequential bullet entrance); pass `motion: 'off'` for formal or print scenarios.
   → Read `references/syntax.md` before using tables, pull quotes, speaker notes, or structured slides.
5. **Read the result**: Use returned file paths, revision and warnings. On success, proceed to delivery. Do not run ppt_check merely to confirm success or obtain a revision already returned. Do not automatically render/re-render, inspect PNGs, run pixel/font-metric scripts, or modify content to satisfy estimates. For a reported defect, diagnose only the affected scope and make the requested fix using expectedRevision. A new visual render is needed only if it will be used to assess the change or was explicitly requested; automatic PDF export by the plugin is separate from a review cycle. If the user requested extended review, agree its scope, perform relevant checks and report actual limits. If image viewing is unavailable, disclose that immediately and deliver for the user's inspection without delegation or model setup.
6. **Deliver**: Inside DSH, provide only the absolute `htmlPath`, `pptxPath` and `pdfPath` (when present). PDF is exported automatically from the final PPTX; when unavailable or failed, deliver HTML/PPTX and explain `pdfWarning`. Never attach the project JSON, page PNGs, manifests or render receipts by default. New project JSON files are kept permanently in `DSH_HOME/plugins/dsh-ppt/projects`; use the returned `jsonPath` internally for editing, checks and undo. Render files live in `DSH_HOME/plugins/dsh-ppt/tmp` and expire after 90 days without use; cleanup runs on plugin startup and before a new cached render. Old projects are not migrated. HTML plays offline in a browser and PPTX opens in PowerPoint / WPS / Keynote. In DSH, the latest deliverables are also available under Settings → Presentation. Cross-harness CLI builds retain the portable HTML/PPTX/JSON trio unless explicitly configured for internal project storage. Session isolation: use the exact paths returned by this invocation. Do not scan a shared workspace, plugin projects directory or global tmp to discover your outputs; those may contain other chats' files. With a host session ID, default deliveries use `<cwd>/dsh-ppt/session-<hash>` and render caches use `tmp/session-<hash>`. Put any requested evaluation records/logs in the returned `outputDir`, and attach only files created for the current request. Do not enumerate all files in cwd for delivery. Explicit separate output directories remain supported; avoid selecting a shared directory unless the user requested it.

## Delivery checklist (no additional calls required)

- Scope, template/style and content were confirmed; supplied facts and requested slide count are preserved.
- The operation succeeded and returned the delivery paths and current revision; use those exact values.
- Deliver available HTML/PPTX/PDF. Disclose relevant warnings and PDF failure without treating advisory estimates as confirmed defects.

## Structured slides and semantic diagrams

Before composing template slide elements, read `ppt_template get` and map each intended purpose to the returned reference IDs, names and purposes. Selection uses explicit `designLayout` first (even if its reference has another purpose); otherwise an exact purpose match, then the first `content` reference for non-cover slides only. There is no implicit content fallback for `cover`. If a suitable title reference is marked `content`, explicitly set its known ID while keeping `purpose:'cover'`. Imported templates may mark every reference `content`; do not infer a cover tag from appearance or page order, guess an ID, or change the slide's semantic role merely to bypass an error. For closing/section slides, specify an ID if the automatic first-content fallback is not the desired design. Resolve this mapping before submitting the full deck; unknown explicit IDs are errors, not invitations to choose a fallback.

Use compositionGuides from ppt_template get: choose the actual title/body reference, consider text anchors, typography, decor, real pictures, captions and neighboring blocks, then choose sizes and wrapping and pass final frames in EMU. referenceArea is a sample, not a capacity quota or exclusion mask. For an unrotated right anchor R, choose width W and x = R - W: R=94 with W=40 gives x=54; W=55 gives x=39. Paragraph alignment alone does not position the block. Rotated/reflected bounds are not the typesetting frame; preserve frame/transform semantics. New content may have different widths, heights and block counts. Do not shorten user text or shrink fonts merely to match the sample. Guides describe the first meaningful run, not all mixed styles. This is initial composition guidance, not a fit guarantee or a reason for automatic metric/render/repair loops. For explicit fixed-slot filling, request includeFixedSlots:true; this preserves original frames and requirements.


### Editing and recovery

Use the latest returned revision and known target data. If either is missing or stale, read the target slide with `ppt_check {deckPath, slide:5}`. It returns `selectedSlide` including complete elements and template decor. For ordinary changes use `ppt_edit {deckPath, expectedRevision, edits:[{slide:5, patch:{elementUpdates:[{id:'existing-text-id',changes:{paragraphs:[{runs:[{text:'Updated',style:{color:'#FFFFFF'}}]}]}}]}}]}`. IDs must exist and be unique. Supplied object fields replace those fields; `textStyle` merges with existing typography. Read and retain all other paragraphs/runs and their formatting when changing only part of a text object. Omitted objects, frames, IDs and drawing order are preserved. This mode cannot add/remove objects or change their type/ID.

`patch.elements` remains a **full replacement of every element**, including template decor. Supply the complete array with unchanged objects and full frames; omitted elements are deleted. `designLayout` does not recreate deleted decor during editing. Do not combine `elements` and `elementUpdates`. Structural changes use the full replacement path deliberately.

After an output serialization or transport error, the operation may already be committed. Check the known project path, revision and content before retrying. A stale `expectedRevision` must not be bypassed. For unwanted edits, use `ppt_undo` with the current revision and inspect the restored version; several saved edits may require several undo steps. Prefer history recovery before rebuilding.

`ppt_create overwrite:true` replaces same-name delivery files but always creates a new internal JSON project, new `deckId`, revision 0 and empty history. It does not repair the old JSON. Continue using the returned `jsonPath`; old projects sharing those delivery paths may report artifact conflicts. `saveAs:true` creates a separate copy from the selected JSON. Never identify the current project by newest-directory shell commands (`ls -t | head -1`); use its path/ID and verify its session and task.

### Units, colour and fonts

`frame.x/y/w/h`, text-frame margins and table row/column dimensions use integer EMU (914400/inch). `stroke.width` and table border widths use **points, 0–100, default 1**, not EMU: 9525 EMU = 0.75 pt, 19050 EMU = 1.5 pt. Font size, paragraph `spaceBefore`/`spaceAfter` and `lineSpacing` kind `pts` use points; `lineSpacing` kind `pct` uses a ratio (1 = 100%). Do not guess or clamp invalid units.

An explicit run/element `color` overrides an inherited `colorSpec`; supplying both explicitly makes `colorSpec` authoritative. Imported colour transforms remain intact when colour is not overridden. Do not duplicate every colour in `colorSpec` as a workaround.

Do not infer unavailable fonts solely from missing system installation: templates and the user's font library can embed font files. Distinguish untested availability from confirmed substitution. When a render has been requested, use its actual `missingFonts` and identify the missing family/style. Re-render only when needed for the requested review; do not launch a font-replacement loop. An empty missing-font list is the renderer's report, not proof of identical typography on every target machine.

Do not claim that Arial or any replacement font is guaranteed on the recipient's machine without evidence. Missing-font render warnings do not establish the cause of static overflow warnings: those are separate checks. Treat substitution/metrics as a hypothesis unless measured; do not automatically replace a requested template font or enlarge blocks on that assumption. `ppt_check` without `renderReceipt` reports that the render is not verified by that check; it does not mean no render exists. Pass the receipt to validate the current PPTX against existing render output.

Use `layout:scene` with `elements` when a slide needs several independent blocks, charts or tables. Set `layout:"scene"` on EVERY such slide; `designLayout` does not replace it. Every new element must include `frame:{x,y,w,h}` with integer EMU coordinates and dimensions, including text, shapes and lines. The template does not position newly invented IDs. Minimal text object: `{id:"title",type:"text",frame:{x:500000,y:500000,w:7000000,h:800000},paragraphs:[{runs:[{text:"Conclusion"}]}]}` (choose actual geometry for the selected page). Geometry is integer EMU (914400 EMU/inch); preserve the original `style.pageSize` for print and screen decks. Do not force 16:9. The `elements` array is drawing order. Every object has a stable ID; edits replace `elements` while retaining IDs of unchanged objects. Text uses paragraphs, runs and explicit breaks; preserve bold, colour and alignment on the relevant runs/paragraphs.

For schema 3 templates, normally pass `templateId` and freely composed scene `slides`. Each slide has `purpose` (cover/content/section/closing), optional `designLayout` referencing an existing template page, and new content `elements`. The engine copies only fixed decor and backgrounds; sample text and required slots do not constrain this path. The first text element inherits heading defaults, later text elements body defaults; copy explicit run styles when needed. Preserve useful body content, not just headings.

Native shapes: `type:'shape'`, `preset:'rect'|'roundRect'|'ellipse'|'triangle'|'diamond'`, `fill:{color,opacity?}`, `stroke:{color,width?}`. Add text as a separate element above the shape; use lines for connectors and groups for related objects. Frames use integer EMU. Images reference embedded assets. Charts and tables retain editable data. Decide composition from content, not a prescribed structure quota.
A list may become a diagram only when its semantics justify the choice:

- Ordered actions → `layout:diagram`, `diagram:{kind:process,items:[{id,label,detail}]}`.
- Explicit dates and milestones → `kind:timeline`, with `date` on each item in the supplied order.
- Alternatives with comparable attributes → `kind:comparison`.
- Explicit parent/child relationships → `kind:hierarchy`, with `parentId`.
- Explicit links between entities → `kind:relationship`, with `links:[{from,to}]`.
- Actual quantitative categories and series → `kind:chart`, with `chart:{kind,categories,series:[{name,values}]}`. No invented numbers, equal weights or fake proportions to make a diagram look quantitative.

For new semantic input always set `diagram.version:2`. Process requires `ordered:true`; timeline also requires valid ISO dates/months in supplied order; cycle requires `repeats:true`. Process, timeline, cycle and relationship support at most 6 nodes; split longer sources explicitly. Cards and hierarchy support up to 12 items. Comparison requires 2–4 alternatives, 1–8 shared `criteria` and matching `values` strings/nulls. KPI requires 1–6 finite values with units; deltas need explicit values and units. Quote and number require exactly one item and a `source`; number also requires a value and unit. Never invent attribution or data.

Keep every supplied label/detail/date. Diagrams are native editable shape/text/line objects, not screenshots or SmartArt. Native charts contain embedded Excel workbooks. Confirmed variants: column, bar, line, pie, doughnut, area, stacked-column, percent-stacked-bar; scatter is unsupported. Pie/doughnut need parts of one whole; line needs meaningful order; stacking needs additive comparable data. A regular list remains a list when relationships are unknown. Choosing a template must not replace explicitly supplied scene/diagram content with sample slides.

`deckPlan` and `templateSelections` remain available for explicit fixed-slot workflows and old projects. Only for that path inspect slot IDs, fill typed values and validate `deckPlan` before create; do not combine with free scene slides. Do not require new template variants, rhythm policies or capacity descriptions for ordinary generation. Do not claim visual acceptance from generation or static estimates; rendering/inspection are optional unless requested.
`ppt_edit convertToScene:true` explicitly migrates a legacy project and all history snapshots. It aborts without writing when bindings or unsupported content cannot be preserved. Mixed legacy content fields and `elements` on one slide are errors, including empty legacy fields. Do not remove fields merely to bypass that error.

Treat import warnings as object-specific limitations, not success: report slide, object ID/name, preservation mode and reason. OLE attachments are never executed or copied into assets; only validated raster previews may be retained. HTML chart previews preserve data but do not guarantee Office chart typography/layout parity. Only claim visual fidelity if the requested inspection actually supports it; no automatic render loop is required.


### Templates with headings and semantic typography

For schema 3, fill independent heading/title slots as well as the content region. A semantic visual replaces only its addressed text slot; do not put the slide heading into that diagram or overwrite source/fixed artwork. `builtin:working-report` supplies heading/body/source slots and three variants. Its explicit textStyles control KPI values, comparison headings, labels and criteria; do not override fonts or scale sizes yourself. Select a sufficiently large region and split long material explicitly when necessary. Rendering and further review are opt-in; successful generation can be delivered with known limitations.
