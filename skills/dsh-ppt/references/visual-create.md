# Компактное содержание в обычном ppt_create

С ru.24 поле `visualSpec` передаёт содержание без координат и использует детерминированную композицию на согласованном библиотечном шаблоне schema 3. Это обычный ppt_create, без start/submit, эксперимента и требования конкретной модели. Уточнение задачи и согласование шаблона выполняются по существующим правилам с учётом уже полученных ответов пользователя.

Актуальный проверенный контур: ru.36, компоненты 15. Серверные примеры восьми типов, смешанной колоды, портретного A4, диаграмм и правки с отменой приняты в пределах указанных сценариев. [Сводка свидетельств и ограничений](../../../docs/FEATURE-PLAN-COMPACT-GENERATION-2026-11-20.md). Это не приёмка любых шаблонов и не выбор победителя A/B/C.

```json
{
  "title": "Направления работы",
  "lang": "ru",
  "templateId": "<согласованный доступный ключ библиотеки>",
  "visualSpec": {
    "version": 1,
    "mode": "demo",
    "allowMoreSlides": true,
    "sources": [{"id": "example", "text": "Демонстрационные данные: Альфа — подготовка, статус Беты неизвестен. Описания: Полное описание первого направления. Полное описание второго направления. Север — 17 заявок, Юг — 9.", "synthetic": true}],
    "slides": [
      {"id": "projects", "title": "Два направления", "visual": {
        "type": "cards", "sourceRefs": ["example"],
        "items": [
          {"id": "alpha", "label": "Альфа", "detail": "Полное описание первого направления.", "iconId": "check"},
          {"id": "beta", "label": "Бета", "detail": "Полное описание второго направления.", "iconId": "clock"}
        ]
      }},
      {"id": "register", "title": "Реестр направлений", "visual": {
        "type": "table", "sourceRefs": ["example"],
        "headers": ["Направление", "Статус"], "rows": [["Альфа", "Подготовка"], ["Бета", null]]
      }},
      {"id": "requests", "title": "Заявки по регионам", "visual": {
        "type": "chart", "sourceRefs": ["example"], "kind": "column", "unit": "заявок",
        "categories": ["Север", "Юг"], "series": [{"name": "Заявки", "values": [17, 9]}]
      }}
    ]
  }
}
```

Каждый элемент slides — один смысловой content-слайд: id, title, visual; notes и designLayout необязательны. Не планировать физические страницы вручную и не добавлять обложку ради заполнения шаблона. Шаблон сохраняет размер, фон, фиксированный декор, палитру и типографику. Без designLayout выбирается подходящий content-макет внутри этого же шаблона с меньшим числом страниц, затем с большей доступной областью. Явный ID не заменяется. Неизвестный/недоступный шаблон и ошибка вместимости не разрешают скрытую подмену.

С ru.29 поддержаны восемь типов; их можно сочетать в одной колоде в порядке slides:

- process: ordered:true и 3–5 items с id, label, необязательными detail/sourceRefs. Порядок должен быть явно задан источником; не превращать неупорядоченный перечень в процесс. Продолжения сохраняют сквозную нумерацию этапов.
- timeline: ordered:true и 2–6 items с id, label, date, необязательными detail/sourceRefs. date — существующая календарная дата YYYY-MM-DD или месяц YYYY-MM; порядок хронологический. Не придумывать день для известного только месяца, не сортировать молча неправильный вход.
- comparison: 1–8 уникальных criteria и 2–4 items с id, label, values той же длины; detail/sourceRefs необязательны. values — строки или null; неизвестное отображается как «—», а не ноль. Сохранять единые критерии и полные пояснения. Результат — нативная таблица.
- big_number: 1–2 items с id, label, явным числовым value и строковым unit; detail/sourceRefs необязательны. Сохранять единицы и оговорки. Ноль допустим, неизвестное число — нет; не заменять неизвестное нулём.
- image: assetId, alt, sourceRefs; caption необязателен. assetId ссылается на visualSpec.assets. Изображение размещается целиком с сохранением пропорций (contain); подпись — отдельный текстовый объект. В PPTX сохраняются исходные байты PNG/JPEG и альтернативный текст. Изображение не делится на страницы; слишком длинная подпись отклоняется без сокращения.
- table: sourceRefs, headers (1–8 колонок), rows (1–30 строк одинаковой с headers ширины). Ячейки — строки или null, без числового преобразования; null отображается как «—». Сохранять все символы, абзацы и неразрывные пробелы. При разрешённом переносе заголовки повторяются, высокие строки продолжаются по частям с диапазонами исходного текста в visualComposition.
- cards: 2–4 items с уникальными id и label; detail, sourceRefs и iconId необязательны. caption необязателен и относится к содержанию. Нативные иконки: check, clock, target, trend. Сохранять полные пояснения и оговорки, не заменять их короткими названиями.
- chart: kind column/bar/line/pie, unit, 1–24 categories, 1–4 series с name и числовыми values той же длины, sourceRefs. line требует ordered:true, pie — whole:true и корректных частей одного целого. Не объявлять произвольное сравнение долями целого. Неизвестные числа не заменять нулём; при недостатке фактов уточнить данные или использовать подходящий обычный путь content/scene. Поддерживаемые ограничения chart проверяются общим семантическим валидатором.

Общий предел: 1–120 смысловых слайдов, 1–64 источника. Лимиты label/detail и остальных строк определены публикуемой схемой. Ссылки на источники, ID и типы проверяются до экспорта; проверка sourceRefs не доказывает истинность или полноту содержания. Синтетические источники требуют demo с видимой пометкой на каждой физической странице.

По умолчанию allowMoreSlides:false. Явное true разрешает перенос строк/частей высоких строк таблиц, целых карточек, этапов process/timeline, показателей big_number, критериев comparison и категорий column/bar с сохранением данных и порядка, без уменьшения шрифта или удаления текста. Одиночный элемент, не помещающийся целиком, отклоняется; продолжение высокой строки поддержано только для table. Сравнение повторяет варианты и пояснения на страницах критериев. Отдельная слишком высокая карточка отклоняется; её текст не делится молча. Pie и line не разбиваются на частичные диаграммы. Действуют общий maxSlides и отмена. Экспорт остаётся нативным и редактируемым; это не гарантия вида в конкретном Office или PDF.

visualSpec нельзя смешивать с верхнеуровневым tableSpec, content, slides, deckPlan, generationPolicy, templateSelections, templateSamples, template, dataModel, assets, style, brand или theme. Для смешанной колоды передавать таблицы как visual.type:table внутри того же visualSpec.slides, не добавлять отдельный tableSpec. Прежний tableSpec поддерживается для табличных колод без изменения контракта. Другие компоненты и титульные страницы продолжают использовать существующий content/scene; это поле пока их не поддерживает. Вызовы без visualSpec не переключаются автоматически.

Необязательный contentHash предназначен для подготовленного проверенного JSON. Интеграция вычисляет `visualCreateContentHash(visualSpec)` из `scripts/deck-visual-create.mjs`: SHA-256 UTF-8 JSON канонического объекта `{mode,sources,slides}`, где sources имеют `{id,text,synthetic:synthetic??false}`, slides — `{id,title,visual,notes:notes??null}`. Ключи объектов рекурсивно сортируются, массивы и все символы строк сохраняются; allowMoreSlides и designLayout не включаются. Не удалять и не пересчитывать переданную сумму ради принятия изменённых данных. Алгоритм отличается от исторического tableSpec.contentHash; использовать helper соответствующего входа.

Выдача обычная: HTML/PPTX/PDF при наличии рендерера, постоянный внутренний проект и текущая ревизия, сессионные пути и права библиотеки. visualComposition содержит разбиение и `visualAcceptance:not-verified`. После успеха выдавать файлы и существенные предупреждения без автоматического цикла дополнительных проверок. Серверный пример трёх карточек и column на public:dkp принят пользователем на ru.24. Смешанный пример ru.25 (карточки, 30 строк таблицы, column) на том же шаблоне прошёл серверную проверку; пользователь подтвердил приемлемый внешний вид. Это приёмка указанного примера, а не всех шаблонов и вариантов.


Типы process/timeline/comparison/big_number подключены к обычному пути в ru.26. Четыре локальных страницы на public:dkp просмотрены в PowerPoint; серверный архив 1301 подтвердил точную сохранность содержания и приемлемую по осмотру компоновку PDF. После отзыва о выравнивании горизонтальные process/timeline центрируют текст под узлами (ru.28, компоненты 9). Архив 1315 подтвердил центрирование и сохранность содержания; пользователь оценил четыре страницы как «визуально приемлемо». Проверенный пример принят; алгоритм contentHash не изменён.

Для подготовленного JSON с исходным contentHash с ru.27 предпочтителен [requestFile/requestSha256](create-request.md): чтение выполняет сам плагин без переноса текста через аргументы модели. Суммы файла и содержания проверяются независимо; нельзя заменять их для принятия изменённого входа.


## Исходные изображения — ru.29

Необязательное visualSpec.assets — массив из 1–16 записей `{id,mime,width,height,data}` с уникальными ID. mime: image/png или image/jpeg; width/height — реальные целочисленные размеры; data — исходные байты в data URI с base64. Не передавать URL, файловые пути, SVG или стили. До экспорта проверяются кодировка, формат, соответствие размеров и MIME, до 5 MiB на картинку и до 8 MiB суммарно. ID не должен конфликтовать с ассетами шаблона. Верхнеуровневое assets при visualSpec по-прежнему запрещено.

Подготовщик JSON читает оригинальные байты локального изображения и кодирует base64 программно; модель не должна набирать/восстанавливать base64. Передавать такой запрос через requestFile. Сохранять alt и подпись по источнику; не подменять предоставленное изображение сгенерированной иллюстрацией. Роль изображения и источник согласуются по уже полученным указаниям пользователя.

Для входа с assets функция visualCreateContentHash дополнительно включает assets в исходном порядке: `{id,mime,width,height,sha256}`, где sha256 вычислен от декодированных исходных байтов. Остальной алгоритм прежний. Подмена картинки при старом contentHash отклоняется. Входы без assets сохраняют прежние суммы. requestSha256 независимо проверяет весь файл, включая base64 и формат JSON.

Локально PNG и JPEG разных пропорций проверены в нативном PPTX и PowerPoint. Серверный архив 1343 подтвердил исходные байты, пропорции 2:1 и 1:2, отсутствие crop, подписи и alt. Пользователь подтвердил видимость всех углов, сохранение пропорций и читаемость подписей. Этот пример на public:dkp принят; приёмка не распространяется на все шаблоны и предельные входы.


## Диаграммы и подписи: актуальное поведение ru.36

В каждом chart задаются исходная unit, категории и числовые серии. Единицу не подменять и масштаб сумм не менять. Несколько рядов передаются как несколько объектов series одной диаграммы, с исходными именами; легенда показывает их различие. Серверный пример двухрядных column/line из исходного текста принят в архиве 1646. Line требует ordered:true и реального порядка категорий. Для pie нужны whole:true и части одного целого.

В обычном pie подпись всегда содержит исходное число и единицу: «Оборудование: 50 тыс. ₽». Необязательное visual.showPercent=true добавляет процент от фактической суммы: «Оборудование: 50 тыс. ₽ (50%)». По умолчанию процентов нет; для других kind параметр showPercent не передаётся. Число и все части единицы связываются неразрывными пробелами в создаваемой подписи, исходная строка unit не меняется. Длинное тире в новых подписях не используется. Целые проценты округляются независимо и могут не дать ровно 100% в сумме.

Новые автоматически оформленные pie сохраняют в проекте amountLabels, поэтому числовая правка через плагин пересчитывает суммы и опциональные проценты. Старые проекты и ручные подписи без связи не мигрируются автоматически. При внешнем редактировании PPTX в Office собственный текст таких подписей сам не обновляется; изменять данные и пересчитывать подписи следует через плагин.

## Короткая правка чисел и отмена

Использовать текущие deckPath/expectedRevision и известный ID диаграммы. Если ID или состояние неизвестны, достаточно адресного ppt_check нужной страницы. Для замены только чисел передавать chartValues, без повторного набора chart, стилей и текстов подписей:

```json
{
  "deckPath": "<актуальный путь проекта>",
  "expectedRevision": 0,
  "edits": [{
    "slide": 2,
    "patch": {"elementUpdates": [{
      "id": "<известный ID диаграммы>",
      "changes": {"chartValues": [[80, 60, 60]]}
    }]}
  }]
}
```

Здесь ревизия 0 только пример: брать её из последнего успешного ответа. Внешний массив содержит по массиву значений на каждую существующую серию, в текущем порядке; число значений соответствует категориям. Движок сохраняет имена, категории, геометрию, оформление и связь подписей. Нельзя сочетать chartValues и полный chart в одной правке. Неверные данные отклоняются до записи, повтор одинаковых значений не создаёт ревизию.

Для отмены использовать ppt_undo с актуальными путём и ревизией ответа edit. Внутренний JSON проекта не прикладывать; выдавать HTML/PPTX/PDF при наличии и предупреждения. После успешной операции дополнительный check/render не обязателен. При ошибке не повторять неизменённый ошибочный аргумент; если результат записи неясен из-за транспорта, сначала адресно прочитать состояние. Если нужны оба состояния, скопировать выдаваемые файлы edit до undo, поскольку рабочие файлы будут заменены.
