# Карточки и диаграммы в обычном ppt_create

С ru.24 поле `visualSpec` передаёт содержание без координат и использует детерминированную композицию на согласованном библиотечном шаблоне schema 3. Это обычный ppt_create, без start/submit, эксперимента и требования конкретной модели. Уточнение задачи и согласование шаблона выполняются по существующим правилам с учётом уже полученных ответов пользователя.

```json
{
  "title": "Направления работы",
  "lang": "ru",
  "templateId": "<согласованный доступный ключ библиотеки>",
  "visualSpec": {
    "version": 1,
    "mode": "demo",
    "allowMoreSlides": true,
    "sources": [{"id": "example", "text": "Демонстрационные данные: Альфа и Бета; Север — 17 заявок, Юг — 9.", "synthetic": true}],
    "slides": [
      {"id": "projects", "title": "Два направления", "visual": {
        "type": "cards", "sourceRefs": ["example"],
        "items": [
          {"id": "alpha", "label": "Альфа", "detail": "Полное описание первого направления.", "iconId": "check"},
          {"id": "beta", "label": "Бета", "detail": "Полное описание второго направления.", "iconId": "clock"}
        ]
      }},
      {"id": "requests", "title": "Заявки по регионам", "visual": {
        "type": "chart", "sourceRefs": ["example"], "kind": "column", "unit": "заявок",
        "categories": ["Север", "Юг"], "series": [{"name": "Заявки", "values": [17, 9]}]
      }}
    ]
  }
}
```

Каждый элемент slides — один смысловой content-слайд: id, title, visual; notes и designLayout необязательны. Не планировать физические страницы вручную и не добавлять обложку ради заполнения шаблона. Шаблон сохраняет размер, фон, фиксированный декор, палитру и типографику. Без designLayout выбирается подходящий content-макет внутри этого же шаблона с меньшим числом страниц, затем с большей доступной областью. Явный ID не заменяется. Неизвестный/недоступный шаблон и ошибка вместимости не разрешают скрытую подмену.

Поддержаны только два типа; их можно сочетать в одной колоде:

- cards: 2–4 items с уникальными id и label; detail, sourceRefs и iconId необязательны. caption необязателен и относится к содержанию. Нативные иконки: check, clock, target, trend. Сохранять полные пояснения и оговорки, не заменять их короткими названиями.
- chart: kind column/bar/line/pie, unit, 1–24 categories, 1–4 series с name и числовыми values той же длины, sourceRefs. line требует ordered:true, pie — whole:true и корректных частей одного целого. Не объявлять произвольное сравнение долями целого. Неизвестные числа не заменять нулём; при недостатке фактов уточнить данные или использовать подходящий обычный путь content/scene. Поддерживаемые ограничения chart проверяются общим семантическим валидатором.

Общий предел: 1–120 смысловых слайдов, 1–64 источника. Лимиты label/detail и остальных строк определены публикуемой схемой. Ссылки на источники, ID и типы проверяются до экспорта; проверка sourceRefs не доказывает истинность или полноту содержания. Синтетические источники требуют demo с видимой пометкой на каждой физической странице.

По умолчанию allowMoreSlides:false. Явное true разрешает перенос целых карточек и категорий column/bar с сохранением данных и порядка, без уменьшения шрифта или удаления текста. Отдельная слишком высокая карточка отклоняется; её текст не делится молча. Pie и line не разбиваются на частичные диаграммы. Действуют общий maxSlides и отмена. Экспорт остаётся нативным и редактируемым; это не гарантия вида в конкретном Office или PDF.

visualSpec нельзя смешивать с tableSpec, content, slides, deckPlan, generationPolicy, templateSelections, templateSamples, template, dataModel, assets, style, brand или theme. Таблицы используют tableSpec. Другие компоненты, изображения, титульные страницы и смешанные колоды с таблицами продолжают использовать существующий content/scene; это поле пока их не поддерживает. Вызовы без visualSpec не переключаются автоматически.

Необязательный contentHash предназначен для подготовленного проверенного JSON. Интеграция вычисляет `visualCreateContentHash(visualSpec)` из `scripts/deck-visual-create.mjs`: SHA-256 UTF-8 JSON канонического объекта `{mode,sources,slides}`, где sources имеют `{id,text,synthetic:synthetic??false}`, slides — `{id,title,visual,notes:notes??null}`. Ключи объектов рекурсивно сортируются, массивы и все символы строк сохраняются; allowMoreSlides и designLayout не включаются. Не удалять и не пересчитывать переданную сумму ради принятия изменённых данных. Алгоритм отличается от исторического tableSpec.contentHash; использовать helper соответствующего входа.

Выдача обычная: HTML/PPTX/PDF при наличии рендерера, постоянный внутренний проект и текущая ревизия, сессионные пути и права библиотеки. visualComposition содержит разбиение и `visualAcceptance:not-verified`. После успеха выдавать файлы и существенные предупреждения без автоматического цикла дополнительных проверок. Живой серверный результат нового поля ещё требуется проверить; успешные локальные тесты не являются его визуальной приёмкой.
